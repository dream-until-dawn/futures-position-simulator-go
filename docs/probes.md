## 2. 结算价的来源：五家交易所的公开日行情

**结算价不是行情，是交易所的结算结果**，无法从 K 线推出来（成交量加权 + 各所自己的
规则 + 无成交时的特殊处理）。逐日盯市的每一分钱都挂在它上面，所以它必须有稳定来源。

| 交易所 | 端点 | 结果 | 格式 | 含结算价字段 |
|---|---|---|---|---|
| 上期所 SHFE | `https://www.shfe.com.cn/data/tradedata/future/dailydata/kx20260904.dat` | **200**，122 679 B | JSON | `SETTLEMENTPRICE` `PRESETTLEMENTPRICE` |
| 上期能源 INE | `https://www.ine.cn/data/tradedata/future/dailydata/kx20260904.dat` | **200**，27 544 B | JSON（与 SHFE 同构） | 同上 |
| 中金所 CFFEX | `http://www.cffex.com.cn/sj/hqsj/rtj/202609/04/index.xml` | **200**，489 092 B | XML | `presettlementprice` `settlementpriceif` |
| 郑商所 CZCE | `https://www.czce.com.cn/cn/DFSStaticFiles/Future/2026/20260904/FutureDataDaily.txt` | **200**，37 944 B | 竖线分隔文本 | `昨结算` `今结算` `交割结算价` |
| 广期所 GFEX | `POST http://www.gfex.com.cn/u/interfacesWebTiDayQuotes/loadList`<br>`trade_date=20260904&trade_type=0` | **200**，17 433 B | JSON | `lastClear` `clearPrice` |
| 大商所 DCE | `POST http://www.dce.com.cn/publicweb/quotesdata/dayQuotesCh.html` | **412** | HTML 表格 | — |

2026-09-04 是周五，即探针当日最近的一个交易日。

三条值得单独记下来的：

- **CZCE 的 `http://` 会 301 到 `https://`**，`curl` 不加 `-L` 直接得到 0 字节且状态码 301。
  这种失败模式很容易被读成「接口挂了」。
- **CFFEX 的 XML 里期货与期权混在一起**（第一条就是 `HO2609-C-2500`），必须按
  `instrumentid` 形态过滤，不能整份当期货吃。
- ⚠️ **DCE 返回 412，加 `User-Agent` 与 `Referer` 后仍是 412。** 它有额外的反爬校验，
  这条**没有打通**。v0.1.0 的 `refdata/live` 会带着这个缺口发布，DCE 的日行情需要
  另找路径（交易所 App 接口 / 会员端下载 / 第三方数据源），或者接受由使用者自行提供。
  **不会拿别家的数据顶替，也不会插值。**

这五（六）个端点是**给使用者取结算价用的**，不是本库的运行时依赖——本库不产生行情，
结算价由回测引擎在结算步喂进来，详见 design.md 的「双层时钟」。

### ⚠️ 上期所那条已经实现了（自然日 2026-09-08）

探过端点不等于取得到数。`refdata/exchange` 把上期所这一条落成了代码，
并且当场做了一次**跨来源核对** —— 那才是它存在的理由：

> 拿柜台自己的结算价去验柜台自己的逐日盯市，是同义反复。

| 合约 | 上期所 `kx20260907.dat` 今结算 | 快期在交易日 20260908 报的昨结算 |
|---|---|---|
| `rb2610` | 3100 | 3100 |
| `rb2701` | 3158 | 3158 |
| `rb2705` | 3189 | 3189 |
| `cu2701` | 108330 | 108330 |
| `ag2702` | 16095 | 16095 |

五个合约、三个品种，两条完全不同的通路，分毫不差。
⚠️ 它顺带去掉了 §10.2 那次外推里的一处循环：此前费额与昨结算价**都来自快期**。

解析上踩到的几处（全部落成测试）：

- `SETTLEMENTPRICE` 是**联合类型**：有值时是数字，没值时是**空字符串**（不是 null 也不是 0）。
  小计行与 TAS 合约都是这样。声明成 `float64` 会让整份文件解析失败；
  声明成 `any` 再断言会**静默丢行**。用 `json.RawMessage` 原样取字节。
- 332 行里丢弃 **31 行**：26 行小计（`DELIVERYMONTH` 是「小计」）与 5 行 TAS（`PRODUCTCLASS` 为 6）。
  ⚠️ 不是「27 + 5」—— 有一行**既是小计又是 TAS**，`PRODUCTCLASS` 先判，
  于是它记在「非期货」那一类里。写成「27 + 5」会让人以为两类互斥，而它们不互斥。
  丢弃逐类计数并可打印 —— 一个静默丢行的解析器，会在上游改格式时给出
  一份看起来完全正常、只是少了几个合约的结果。
- 必须核对文件里的 `report_date`：⚠️ **拿错一天的结算价不会有任何动静**，
  数看起来完全正常，只是错了一天。
- ⚠️ 破坏验证抓到一处装饰：原先写的 `dec.UseNumber()` 删掉之后没有任何测试变红 ——
  保住精度的根本不是它（本结构体里一个 `any` 都没有），是那两个 `RawMessage`。
  装饰在这里比无用更坏：它让人以为精度被照顾过了，于是不再去看真正起作用的那处。

⚠️ 仍然只有上期所一家。其余五家探过端点、**没有实现**，其中大商所返回 412 未打通。
**少一家就是少一家，不拿别家的数据顶替，也不插值。**

## 3. 真值通路一：CTP 口径

中国期货没有「交易所 REST API 返回持仓 JSON」这回事。持仓与资金的权威表述在**柜台**，
而柜台事实上的标准是上期技术的 **CTP（综合交易平台）**。

用 `gitee.com/haifengat/goctp@v1.10.17` 自带的 CTP v6.5.1 定义清点了一遍：

```bash
go mod download gitee.com/haifengat/goctp@v1.10.17
grep -cE '^type CThostFtdc\w+ struct' "$(go env GOMODCACHE)/gitee.com/haifengat/goctp@v1.10.17/ctpdefine/ctp_struct.go"
# 363
```

| 结构体 | 字段数 | 它决定什么 |
|---|---|---|
| `CThostFtdcTradingAccountField` | **49** | 资金账户：结存、可用、保证金占用、各类冻结、平仓盈亏、持仓盈亏 |
| `CThostFtdcInvestorPositionField` | **50** | 持仓：今昨仓、两套盈亏口径、公司保证金与交易所保证金 |
| `CThostFtdcInvestorPositionDetailField` | **31** | 逐笔持仓明细：逐笔对冲口径的盈亏挂在这里 |
| `CThostFtdcInstrumentField` | **35** | 合约规格：乘数、最小变动价位、多空保证金率、大边算法、今昨仓类型 |
| `CThostFtdcInstrumentMarginRateField` | 13 | 保证金率：按金额 / 按手数，多空分开，投机与套保分开 |
| `CThostFtdcInstrumentCommissionRateField` | 14 | 手续费率：开 / 平 / **平今**，各自按金额与按手数 |

这一步不只是数字，它直接定住了几条建模事实，而且是**从定义读出来的，不是回忆的**：

```
CThostFtdcInvestorPositionField 里同时有：
    CloseProfitByDate      逐日盯市口径的平仓盈亏
    CloseProfitByTrade     逐笔对冲口径的平仓盈亏
```

⚠️ **两套盈亏口径同时存在于同一个结构体里。** 这不是历史包袱，是中国期货的实际形态：
资金结算走逐日盯市，而客户看的账单里两个都有。**只实现一套 = 一半的字段对不上**。

```
    UseMargin              期货公司保证金
    ExchangeMargin         交易所保证金
```

⚠️ **保证金也是两层。** 期货公司在交易所标准上加收，两个值都要建模，否则风险度会算错
——风险度用的是公司口径。

```
CThostFtdcInstrumentField 里：
    PositionDateType       UseHistory / NoUseHistory
    MaxMarginSideAlgorithm NO / YES
    LongMarginRatio / ShortMarginRatio                    多空分别给
```

⚠️ **「区分今昨仓」与「单向大边」都是逐合约的开关，不是逐交易所的常识。**
按交易所硬编码（「上期所区分今昨、其余不区分」）在绝大多数合约上都对，
于是错的那几个不会被测出来。**这两个值必须从规则数据里读。**

`OffsetFlag` 的取值也一并确认了，七个：
`Open` `Close` `ForceClose` `CloseToday` `CloseYesterday` `ForceOff` `LocalForceClose`。
——**强平在 CTP 里有三种**（交易所强平 / 强减 / 本地强平），这与「强平是交易所的确定性算法」
的直觉相反，见 fidelity.md。

### Go 通道：Windows 上不需要 cgo

```bash
MOD="$(go env GOMODCACHE)/gitee.com/haifengat/goctp@v1.10.17"
grep -rl 'import "C"' "$MOD"          # 只有 lnx/quote_lnx.go、lnx/trade_lnx.go
grep -oE 'syscall' "$MOD"/win/*.go    # win/ctp_quote.go、win/ctp_trade.go
ls "$MOD/v6.5.1_20200908/win_x64/"    # thosttraderapi_se.dll .lib .h …
```

- **Windows 走 `syscall` 动态加载 DLL，不用 cgo。** 本机开发与对拍不需要 C 工具链
- Linux 才走 cgo（`lnx/*.so`）
- 模块自带 CTP v6.5.1 的头文件、win_x64 的 `.dll`/`.lib`、以及 Linux 的 `.so`

⚠️ 但它仍然是**一个带二进制的第三方模块**。按 design.md 的依赖硬约束，它只能进
`cmd/oracle` 这个**独立嵌套模块**，绝不进主模块。

## 4. 真值通路二：天勤 DIFF —— 更好的那一条

> 这一节是使用者提示「已有快期（天勤）免费账户」之后**追加验证**的。
> 验完的结论是：**它比原方案好**，因此被提升为主对拍口子。
> 但它也有原方案没有的**缺口**，所以 CTP 那条不废，改作权威裁决。

### 协议形态

```bash
curl -sL https://doc.shinnytech.com/diff/latest/general.html | grep -oiE 'json[ -]?merge[ -]?patch|rfc ?7386|rtn_data'
# JSON Merge Patch ×4，rfc7386 ×2，rtn_data ×6
```

**DIFF 是 JSON over WebSocket + JSON Merge Patch（RFC 7386）。**
服务端推 `rtn_data`，客户端把补丁合并进本地业务截面。

⚠️ **这意味着 Go 侧不需要 cgo、不需要 C++ SDK、不需要 DLL** ——
一个 WebSocket 客户端加一份 merge-patch 实现就够了。这是它胜过 CTP 通路的关键。

### 业务截面的字段

从 `funcset/trade.html` 与 `funcset/quote.html` 里逐个提取出来的键名：

**`trade/{user}/accounts/CNY`（18 个）**

```
account_id  currency  pre_balance  static_balance  balance  available  risk_ratio
deposit  withdraw  commission  premium
close_profit  position_profit  float_profit
margin  frozen_margin  frozen_commission  frozen_premium
```

**`trade/{user}/positions/{symbol}`（28 个）**

```
exchange_id  instrument_id  hedge_flag  last_price
volume_long  volume_long_today  volume_long_his  volume_long_frozen_today  volume_long_frozen_his
volume_short volume_short_today volume_short_his volume_short_frozen_today volume_short_frozen_his
open_price_long/short      open_cost_long/short
position_price_long/short  position_cost_long/short
float_profit_long/short    position_profit_long/short
margin_long/short
order_volume_buy_open  order_volume_buy_close  order_volume_sell_open  order_volume_sell_close
```

⚠️ **`float_profit` 与 `position_profit` 并列，`open_cost` 与 `position_cost` 并列。**
天勤原生就分开了「按开仓价」与「按昨结算价」两个基线——正是本库最核心的那条区分
（cn-futures-rules.md §5）。这是个强信号：**这套字段是照着真实柜台的语义设计的。**

**`orders` / `trades`**：`order_id` `direction` `offset` `volume_orign` `volume_left`
`price_type` `limit_price` `time_condition` `volume_condition` `status` `last_msg`
`insert_date_time` `exchange_order_id`；成交侧 `trade_id` `price` `volume` `trade_date_time`。

**`quotes/{symbol}`（34 个）**，含规则数据与结算价：

```
volume_multiple  price_tick  price_decs
max_market_order_volume  min_market_order_volume  max_limit_order_volume  min_limit_order_volume
margin  commission
upper_limit  lower_limit  pre_settlement  settlement  pre_close  open_interest  pre_open_interest
```

### ⚠️ 它给不了的三件事

对拍口子的价值不只看它给什么，更看它**不给**什么——那部分会变成盲区。

1. **只有一个 `close_profit`**，不分 `ByDate` / `ByTrade`。
   两套平仓盈亏口径的分别验证，**只能靠 CTP**
2. **`quotes.margin` / `quotes.commission` 是「每手保证金 / 每手手续费」的单一数值**，
   不是 CTP 的 6 个手续费率 + 4 个保证金率。
   ⚠️ **用它做规则数据会丢掉「平今费率」这个维度**——而日内策略的手续费几乎全落在那上面
3. **快期模拟是天勤自己的模拟撮合与结算，不是 CTP 柜台。**
   「与快期模拟一致」≠「与真实账户一致」，**这个差现在完全未知**

结论：**天勤做主对拍（覆盖广、门槛低、纯 Go），CTP 做权威裁决（补上述三个缺口）。**
详见 [design.md](./design.md) §5。

### 顺带发现：一份公开免鉴权的合约字典

```bash
curl -sL https://openmd.shinnytech.com/t/md/symbols/latest.json
```

**200，无需认证**，约 8 MB，覆盖全市场合约与指数，每条带
`class` `exchange_id` `instrument_id` `ins_name` `volume_multiple` `price_tick` `price_decs` 等。

这解决了 §7 表里「SHFE 的合约参数端点全 404」那个缺口——合约规格不必去爬六家交易所。

### ⚠️ 更正：它是 **334 MiB**，不是 12.5 MB —— 我量错了 27 倍

本文档先前写着「约 12.5 MB 且很慢」，后来改成「16.3 MB 仍未完整」。**两个都是错的。**
2026-09-07 用一个 Range 请求当场量准：

```
curl -r 0-100 https://openmd.shinnytech.com/t/md/symbols/latest.json
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 0-100/350177909      ← 350,177,909 字节 = 334 MiB
```

⚠️ **我量的是「我下了多少」，不是「它有多大」。** `ls -la` 量的是那个被截断的
本地文件，而它每次断在不同的地方，于是我每次都得到一个不同的、看起来合理的数。

⚠️ **而且我从没试过 Range** —— 但原因不是我以为它不可用。

> **更正一次归因错误。** 本文档先前写着「上游数据层一度以为服务端会忽略 Range，
> 我照单收下没验」。**这句两处都错**：
> (a) 上游没在消息里对我说过这句（他说的是「要 `-C -` 续传」，
>     而 `-C -` 恰恰**要求** Range 可用）；
> (b) 本库自己的历史文档写的是「完整性校验 + **断点重试**」——
>     **我一直相信续传可用。**
>
> 把自己的疏忽算到别人头上，比疏忽本身更难查，因为它会让复盘停在错的地方。

真实的形状是另一种，而且更难防：

> **工具就在手里，我从没想到用它去量。**
> 不是被一个错误挡住了，是**我不知道有东西需要量**——那个数字从没被怀疑过。

⚠️ 所以「两个错互相掩护」是**上游那边**的形状，不是本库这边的。
本库这边是「一个错 + 一个从未被触发的疑问」。两者的修法不同：
前者要打破错误之间的相互掩护，后者要**有一个能触发疑问的信号**。

按实测约 1.3 MB / 3 分钟，全量下载要 **13 小时左右**。

### 正确用法：Range 取片段，不整包下载

判「端点在不在 / 结构对不对 / 总量多大」，一个 256 KB 的 Range 请求就够：

```
curl -r 0-262143 …            256 KB
→ 269 条完整条目，volume_multiple / price_tick / price_decs / margin /
  commission / trading_time / expire_datetime 全部在内
```

⚠️ **这不改变 refdata 的选型，反而印证了它**：design.md 早已把 refdata 的主源
定为**柜台**（`ReqQryInstrument` 等），这个端点从来只是便利与交叉验证的通道。
把它当主源规划过的人，会按「12.5 MB，慢一点而已」去做，然后撞上 13 小时。

### ⚠️ 更正：截断的危险不在解析器上，在「修补」上

本文档先前写着「如果截断恰好落在两条记录之间，它会静默地少几个合约」。
**这句是错的**，2026-09-07 由上游数据层指出，本库两个语言各验一遍：

```
Python  截断在两条记录之间 → json.JSONDecodeError
Go      同上               → unexpected end of JSON input
【修补后】再解析            → err=nil，静默少 1 条      ← 危险在这一步
```

**标准解析器对截断输入一律报错**——外层容器没闭合，截在哪都一样。
静默丢**只发生在有人自作聪明地把它补全之后**。

这个区别决定了缓解措施完全不同：

| 错的结论 | 正确的做法 |
|---|---|
| 「加一道解析后的数量校验」 | **根本不要修补**：让它自然报错，然后 `curl -C -` 续传重来 |

⚠️ 落盘前必须能**不加任何补全地**完整 `Unmarshal`，失败就续传重来。
这个端点在两边的网络条件下都很难一次拉完，**完整性校验不是可选项**。

## 5. 模拟环境的可达性

```
http://www.simnow.com.cn/    202   （curl 在此域名上段错误，PowerShell Invoke-WebRequest 正常）
http://www.openctp.cn/       200
```

两个都可达。**SimNow**（上期技术官方模拟）是 CTP 通路的对拍环境；
**openctp** 的 TTS 提供 7×24 的 CTP 兼容环境，用于非交易时段的冒烟。

### 6.4 ⚠️ 一个把我自己绊了一下的假阳性

最初判 SimNow「登录超时失败」，是因为两个错误叠在一起：

1. **`goctp` 的 `OnRspUserLogin` 不在登录应答时触发**，而是等整条初始化链路
   （结算确认 + 合约 + 账户 + 持仓查询）跑完才触发。链路卡住 → 回调不来 →
   看起来像「登录没有应答」。**改成直接轮询 `TradingDay` 立刻就看到登录早就成功了。**
2. 我先用 TCP 连接测试判前置有效性，得到「两个端口都 CONNECTED」。
   随后扫 30000–30015 发现**十六个端口全部 accept**——这台主机前面有代理，
   **TCP 层的连通性测试对 CTP 前置毫无判别力**。

第 2 条已作为一条方法论写进 [silent-risks.md](./silent-risks.md)：
**一个总是返回「成功」的检查，和一个正确的检查，在成功样本上长得一模一样。**

真正有判别力的做法是**在协议层登录**：行情 API 在 30001 与 30011 上都登录成功，
在 30007 上超时并断开——这才把「有前置」和「没前置」分开。

#### 怎么取的

⚠️ `goctp` 只导出高层 `win.Trade`，而 `ReqQryBrokerTradingParams` 挂在**未导出**的

（⚠️ **不往仓库里放二进制**）。只读，不下单。

两个踩到的坑，都写下来：

    CreateApi 会在**当前工作目录**下写 CTP 流文件，目录不存在直接崩
    （RuntimeError: can not open CFlow file，接 0xc0000005）

    ⚠️ 第一次跑 40 秒没有任何应答，第二次同一个二进制就成功了 ——
    **差别不在代码里**。真实原因未知（频率限制？上个会话没断干净？），
    写不知道，别编（方法论 46/61）。三次运行取到的值一致

#### 现在有可复现的跑法了

⚠️ 上面那段是一次性探针。20260909 已经包成 `cmd/oracle/ctp` 与一个子命令：

    go run . ctp-params -env ../../.env

包出来之后重跑，值一致。⚠️ 与探针相比多做了一件事：**枚举翻成人话**，
而每一个翻译都带 default「⚠️ 没见过的取值」—— 一个没见过的取值必须显式说出来，
打印空字符串会与「这一档没有名字」长得一样。

#### 取到的值

```
MarginPriceType          "4"   THOST_FTDC_MPT_OpenPrice        保证金基准价 = 开仓价
Algorithm                "2"   THOST_FTDC_AG_OnlyLost          盈亏算法 = 只计浮动亏损
AvailIncludeCloseProfit  "0"   THOST_FTDC_ICP_Include          可用**包含**平仓盈利
CurrencyID               CNY
OptionRoyaltyPriceType   "5"                                   期权，本库不建模
```

#### ⚠️ 它当场推翻了本库候选集的形状

`margin.PriceBasis` 的四个候选是**推出来的**，而 CTP 的 `MarginPriceType`
也正好是四个取值 —— 两组**对不上**：

    CTP 的四个                     本库的四个
    1 PreSettlementPrice   ←→      PreSettleAll                ✅ 对上
    2 SettlementPrice      ←→      SettlementAll               ✅ 对上
    3 AveragePrice         ←→      （本库没有）
    4 OpenPrice            ←→      （本库没有）
    （CTP 没有）           ←→      LastAll（连续重估，加密货币形态）
    （CTP 没有）           ←→      OpenTodayPreSettleHistory（今开仓价/昨昨结算价）

> ⚠️ **本库四个候选里有两个不在 CTP 的取值空间里；CTP 四个里有两个本库表达不了。**
> 而 SimNow 实际配的那一个（`OpenPrice`）**正是本库表达不了的**。

⚠️ 根子在于：候选集是**按「哪些价说得通」想出来的**，不是**按柜台的枚举列出来的**。
一个想出来的候选集会**恰好覆盖你想到的那些情形** —— 而它漏掉的那些，
不会以「候选不足」的形式报错，只会以「怎么调都对不上」的形式出现。

#### ⚠️ 三条界限，别把这次观测读大了

    ① 它是**声明**不是**行为**。查到的是 SimNow 这个柜台**配置成什么**，
       而「它是否真按这个算」要有持仓才验得了 —— 账户现在是空的
    ② 它是**broker 9999（SimNow）**的配置。字段名就叫 BrokerTradingParams，
       **按柜台配**是这个参数的定义本身；换一个期货公司可以是别的值
    ③ 因此它**不推翻** kq_facts 1（快期实测昨结算价）——
       两个口子配的不一样，是一件早该预料到的事，而不是谁错了

#### 它同时答了另外两件

    AvailIncludeCloseProfit = Include
      → cn-futures-rules.md §13 第 11 条「平仓**盈利**算不算进可用」：**算**
        ⚠️ 仍是 SimNow 这一个柜台的配置，同样按上面三条界限读

    Algorithm = OnlyLost（只计浮动亏损）
      → 而快期实测是 "1" 浮盈浮亏都计算（kq_facts 11）
        ⚠️ 这是 simnow_pending#4「快期与真实 CTP 的口径差」的**第一份硬数据**：
        差别是**存在**的，而且就在最核心的两个参数上

2. **下单安全阀把平仓也挡了。** `PROBE_MAX_VOLUME=1` 对所有委托一视同仁，
   于是 2 手仓平不掉——一个防止扩大风险的守卫阻止了缩小风险。现在它只管开仓。
3. **同名夹具静默覆盖。** `fee-form` 一趟豆粕一趟螺纹，两个不同样本、两个不同结论，
   第二趟把第一趟整份盖掉。现在按内容判断：相同才覆盖，不同则另存并吼出来。
4. **`status` 读到半截截面**：持仓 4 手而 `margin` 打印成 `0.0000`。
   现在先等截面静默，且在自相矛盾时明说。

这四条的方法论形态见 [silent-risks.md](./silent-risks.md) 第 13、14 条。

### ⚠️ 第 0 步的判据换了：`settlement` 由 `"-"` 变成一个数

日盘的行情快照（`status-20260908-7`）实测到一件原计划没写的事：

> 结算之前，`quotes.<合约>.settlement` 给的是字符串 **`"-"`**，不是 0。

于是「结算发生了没有」有了一个**直接观测**，而不是从 `pre_balance` 推断：

    结算前   settlement = "-"      柜台明说：还没有今结算价
    结算后   settlement = 3160     有了

⚠️⚠️ **上面这段话写完两小时就被实地证伪了，原文保留，改正写在下面。**

原文写的是「`settlement` 出现就是结算本身」。实测（自然日 2026-09-08 日盘收盘）：

    ⚡ [15:00:02.368] quote.SHFE.rb2701.settlement   "-" → 3163.0000
    [15:04] 同一账户的截面：
            trading_day = 20260908      **未变**
            pre_balance = 1000000       **未推进**
            rb2701 多今 3 / 多昨 0       **今仓没有滚成昨仓**

**「今结算价出现」与「账户结算发生」是两件事，而且在时间上分开。**
前者是行情事件（收盘后 2.4 秒），后者是柜台的日终处理（尚未发生）。

于是这条判据的**含义要改**，不是删掉：

| 观察到 | 能断言的 | **不能**断言的 |
|---|---|---|
| `settlement` 由 `"-"` 变成数 | 今结算价已经产生 | ⚠️ 账户结算发生了 |
| `pre_balance` 推进 | 账户结算发生了 | —— |
| 今仓滚成昨仓 | 账户结算发生了**且**滚了今昨 | —— |

⚠️ 把第一行当成第三行用，会在今晚 21:00 得出「结算早就做完了」的错误结论，
而那会让第 0 步的三态判定直接走错分支。

⚠️ 记一条方法论：**一个「不依赖推理」的判据，仍然可能在断言一件别的事。**
原文的推理没错（`settlement` 出现确实不需要推理），错在**它出现所标记的事件不是我要的那个**。
「直接观测」保证的是观测本身可靠，不保证观测的是对的东西。

⚠️ 而这一条差点被记错：`settle-watch` 此前用 `kq.MustNum` 读字段，
`"-"` 会被记成 `0.0000`。结算时「0 → 3160」照样触发，所以**探测**没坏；
坏的是留在夹具里的那句话 —— 柜台说的是「无值 → 3160」。
已改成四态渲染（有值 / 无值 / 缺字段 / 未知类型），见 §11。

### ⚠️ 今结算价已到手，而它带来一个坏消息

| 合约 | 到达时刻 | 今结算价 | 种子明细 | 开仓均价 | 两条基线 |
|---|---|---|---|---|---|
| `SHFE.rb2701` | **15:00:02.368** | 3163 | 3 手 @{3151,3151,3171} | 3157.666… | **不同** ✓ |
| `DCE.m2701` | **15:03:47.368** | 3415 | 3 手 @{3411,3411,3423} | 3415 | ⚠️ **相同** |

两件事：

**一、两家交易所发布今结算价差 3.7 分钟。** 5 分钟间隔的盯盘会把它们混成一次，
甚至只看见其中一个。这是 5 秒细采样白赚到的一条。

**二、⚠️ `m2701` 的今结算价恰好等于它的开仓均价**：`(3411+3411+3423)/3 = 3415`。
于是结算之后它的 `position_price` 被重置成 3415，而 `open_price` 本来就是 3415 ——
**两条基线完全相等，它今晚对「逐日盯市 vs 逐笔对冲」这条区分没有判别力**。

这正是 `Split` 那条守卫写下来时假设的情形（「结算价恰好等于开仓均价时……
对拍会照样全绿」），它在写完几小时后成真了。

⚠️ **补不了**：日盘已收，而夜盘开的仓属于下一个交易日，昨仓的均价已经锁死。

⚠️ 而这件事的分量在于：**幸好种子有两个**。
`rb2701` 保住了这条判别力（3157.666… vs 3163）。
若当初只播一个 `m2701`，今晚整批会在一个什么都验证不了的样本上跑完，**而且全绿**。

> 「种子播两个」当初的理由是覆盖 `UseHistory` 与 `NoUseHistory` 两类合约，
> 而它这次救的是另一回事。**冗余在被用到之前，看起来都像浪费。**

第 4 步（`close-order`）不受影响：它靠的是 `open_price` 在**不同明细**之间的差，
而 `{3411,3411,3423}` 平掉 1 手之后，先进先出剩 3417、后进先出剩 3411，仍然分得开。

### 第 0 步有**三种**结果，不是两种

原计划只写了「滚了 → 往下跑 / 没滚 → 整批作废」，而那把第三种归进了作废：

| 结果 | 判据 | 动作 |
|---|---|---|
| 结算未发生 | `pre_balance` 未推进 | 昨仓批整批作废 |
| 结算发生 + 已滚昨仓 | `pre_balance` 推进，且有昨仓 | 正常往下跑 |
| **结算发生但没滚今昨** | `pre_balance` 推进，仍全是今仓 | ⚠️ **这是一条结论，不是故障** |

第三种若成立，说明**本柜台做日终结算但不滚今昨仓**——
它直接改写第 7 条与第 4 条的前提（那两条问「昨仓怎么算」，而昨仓根本不出现）。
把它归进「作废」，等于把这批里可能最重要的发现丢掉。

⚠️ 判据刻意用**与持仓无关**的指标（`pre_balance` / `close_profit` / `pre_settlement`），
因为「持仓没滚」正是待判的事情之一。

### ⚠️ 第三种结论有一个前提，而它差点被漏掉

干跑这条探针时它当场报出了第三种结论——**那是假阳性**：
基线取的是 20260907，而种子是在 20260908 **之内**建的，
那次结算发生时它根本还不存在。**结算之后才建的仓本来就是今仓，
判它「没滚」是在判一件没到期的事。**

所以判据补了一条前提：**基线截面里必须先有这些今仓**，否则第三种结论无判别力，
探针会明说「判据不成立」而不是给结论。
⚠️ 这条前提是干跑抓到的，不是设计时想到的——**而它落在三个分支里最贵的那一个上**。

### 第 1 步是市场相关的，所以它有时限、且方向中性

「构造一笔为正的平仓盈亏」需要行情配合，而它排在最前且阻塞后面全部。两个约束：

- **方向中性**：同合约开一多一空，行情往哪边走都有一条腿盈利，平掉盈利那条。
  不需要对方向下注——⚠️ **需要押注才能构造的样本，成本和效度会一起随行情走。**
- **20 分钟时限**：等不到就跳过，去跑昨仓批。
  种子过了下一次结算仍然是昨仓，**昨仓批不是一次性的**；
  拿窗口去赌第 1 步，赔率不对。

标的选 `rb`（一个 tick 10 元、盘口活），不选 `cu`（一个 tick 50 元）。
⚠️ 此前算「24 个 tick」用的是 `cu`，那是为了翻当日的 −1190；
新交易日归零之后前提变了，**标的应当重选**。

### ⚠️ 日盘批新加的两条前提

原种子是 `rb2701` 2 手 @3151、`m2701` 2 手 @3411 —— **两手同价**。
那样的话第 4 步（平少于昨仓量）会白做：三种消耗顺序给出**同一个剩余均价**，
实验做完什么都没分开，而这件事要到今晚跑完才会发现。

日盘的 `avg-price` 各加了一手不同价，现在是：

| 合约 | 明细 | 平 1 手之后剩余的开仓均价 |
|---|---|---|
| `SHFE.rb2701` | 3 手 @{3151, 3151, 3171} | 先进先出 3161 / 后进先出 3151 |
| `DCE.m2701` | 3 手 @{3411, 3411, 3423} | 先进先出 3417 / 后进先出 3411 |

⚠️ 而这条判别力**只在 `open_price` 上**：结算会把 `position_price` 统一重置成
昨结算价，逐日盯市那条基线认不出是哪一手被消耗了。逐笔对冲基线永不改变，
正是它在这里的用处 —— 也是 design.md 决策 10 第一次真正被用上。

**二、⚠️ 重放今晚的截面**需要一个起始持仓，而它不在今晚的夹具里。

柜台的成交截面**按交易日重置**。今晚的持仓截面里会有昨仓，
而今晚的成交里**没有任何一笔能解释它** —— 那几手是今天开的。

于是 `Replay(空仓, 今晚成交)` 会漏掉全部昨仓，
而漏掉之后重放出来的持仓**看起来完全正常**，只是手数少了几手，
它会与柜台比出一堆看起来像真差异的差异。

正确的链条是：

    今天的夹具（avg-price-20260908*）
      → 按**今天的结算价**结算   ← ⚠️ 这一步需要一个今天才有的输入
      → 得到昨仓
      → 在其上重放今晚成交       ← ReplayFrom(start, ...)

所以今晚要多取一样东西：**`rb2701` 与 `m2701` 在交易日 20260908 的结算价**。
⚠️ 而它现在有了两条**都已落成代码**的取法：

    柜台    夹具里的 quotes.<合约>.settlement —— 结算后由 "-" 变成数（上一小节）
    交易所  go run ./cmd/settlement -day 20260908 -symbols SHFE.rb2701

### ⚠️ 于是结算判据有了**三条互相独立**的

实测（自然日 2026-09-08 14:4x，日盘尚未收盘）撞到一件事：

> `kx20260908.dat` **已经存在且返回 200**，332 行俱全，
> 而全部 `SETTLEMENTPRICE` 是**空字符串** ——
> 交易所盘中就发布这个文件，结算之后才把价填进去。

**「文件在」不等于「结算发生了」。** 于是：

| 判据 | 来源 | 结算前 | 结算后 |
|---|---|---|---|
| `quotes.<合约>.settlement` | 柜台 | `"-"` | 有数 |
| `pre_balance` 推进 | 柜台 | 未变 | 变了 |
| 交易所日行情的 `SETTLEMENTPRICE` | **交易所** | 空字符串 | 有数 |

前两条同源（都来自柜台），第三条**独立**。
三条同时看是交叉验证；只在它们**分岐**时才需要动脑子 ——
而分岐本身就是一条值得记的观测（比如柜台已滚而交易所未发，或者反过来）。

⚠️ 解析器把这种情形单独判、单独说，不与「解析失败」合并：
合并会让人去查解析器，而真正的原因是「时候未到」。


两个来源都要拿，因为它们互相独立：

| 来源 | 取法 | 性质 |
|---|---|---|
| 柜台 | `quotes.settlement`，结算之后才有值 | 与被测对象同源 |
| 交易所 | SHFE / DCE 的日行情（§2 的端点） | ⚠️ **独立第二来源** |

⚠️ 第二个来源不是冗余：逐日盯市的每一分钱都挂在结算价上，
而拿柜台自己的结算价去验柜台自己的逐日盯市，是同义反复。
（DCE 的日行情端点 §2 记着**没打通**（412），所以 `m2701` 这一侧
今晚大概率只有柜台一个来源 —— 那就照实记成一个来源，不假装有两个。）

## 7.3 日期约定：夹具名与实测记录一律用**交易日**

⚠️ **这条此前存在但一处也没写下来**，而它今晚就会撞车。

夹具文件名里的 8 位日期是 `trading_day`，不是自然日——20 份夹具全都遵守，靠的是我记得。
问题在于交易日与自然日**不是同一个东西**：

    交易日 20260908 的夜盘  →  物理上发生在自然日 2026-09-07 周一晚
    自然日 2026-09-08 的夜盘 →  属于交易日 20260909

于是「2026-09-08 夜盘」这个标签**同时指向两场不同的实验**，
而没有任何字段能把它们分开。⚠️ 这一周它已经制造了两次真实的日期错误
（实现方与评审方各一次）——**能骗过写它的人和评审的人的标签，
也会骗过三个月后的读者**，而那时错的是证据的日期，不是日程。

约定，两条：

1. **夹具名与实测记录里的日期，一律是交易日**，写成紧凑形式：`交易日 20260908`。
2. **凡指自然日必须显式写「自然日」**，并用带横线的形式：`自然日 2026-09-07`。

两种格式因此在**字面上**就分得开，不靠读的人记得是哪一种。

⚠️ 这两条不靠人记：`TestFixtureNameMatchesTradingDay` 断言每份夹具的文件名日期
等于它内部的 `trading_day`；`TestSessionLabelsAreQualified` 断言文档里带横线的
日期紧接「夜盘/日盘」时，前面必须直接写着「自然日」。
**靠记得是条目层的解法，钉在字面上是动作层的解法**——见 [silent-risks.md](./silent-risks.md) 第 26 条。

## 7.3b 时段边界对照组（自然日 2026-09-08 日盘，交易日 20260908）

⚠️ **这一组的价值不在它测出了什么，在于没有它，今晚测出的东西无法归因。**

第 0 步要判「结算做了什么」，做法是拿新交易日的截面与交易日 20260908 的基线比。
但周一夜盘收盘（23:00）到周二日盘开盘（09:00）之间**也隔着一道时段边界**，
而那里**没有结算**。不先量出「只跨时段时什么不变」，
今晚看到的变化就可能只是「又跨了一个时段」。

基线采于自然日 2026-09-07 23:10（夜盘收盘后），现在是自然日 09-08 日盘，
期间 `commission` 与 `close_profit` 均未变动（无成交）：

| 字段 | 基线 | 跨停盘之后 | |
|---|---|---|---|
| `volume_long_today` | 2 | 2 | 今昨仓**不滚** |
| `volume_long_his` | 0 | 0 | |
| `open_price_long` | 3151 | 3151 | |
| `position_price_long` | 3151 | 3151 | 逐日盯市基线**不重置** |
| `margin_long` | 4421.2 | 4421.2 | 保证金**不重算** |
| `last_price` | 3165 | 3157 | 行情（走了 8 个点） |

**行情驱动之外的字段一个都没变。** 于是今晚若这些字段变了，只能归给**结算**。

⚠️ 顺带把保证金基准的证据加强了一档：价格跨时段走了 8 个点而 `margin_long` 分毫不动。
按最新价算应为 3157 × 10 × 7% × 2 = 4419.8。夜盘那次价格只走了 2 个点，
这次的排除力度大得多，而且**跨了一道停盘**。

### ⚠️ 这条探针的判据修了两次，两次的修补各自制造了对方的病

	一跑  取当日**最早**的基线  → 报 22 处「时段边界改动了持仓」
	                              假阳性：基线采于种子建立之前，变的是**我自己下的单**
	二跑  改取当日**最近**的基线 → 挑到 2 分钟前的截面，last_price 3158 → 3158
	                              **一道边界都没跨**，判据空转

合格的对照基线要**同时**满足三条，缺一条就从一头或另一头失效：

1. 同一交易日（否则中间隔着结算，那是 `settle-check` 的事）
2. **此后没有发生过成交**（用 `commission` / `close_profit` 是否变动来核）
3. **与现在不在同一个自然日**（那才保证跨过 23:00–09:00 那道停盘）

⚠️ 第 3 条用**自然日**判，因为时段是墙钟上的东西——这是 §7.3 那条日期约定
在代码里第一次派上用场。

## 7.4 夹具保留策略：只因「被证明是错的」而删，不因「有更新的了」而删

⚠️ 这条规矩是被一次实测逼出来的，而它的论据本身就说明了为什么需要它。

`static_balance = pre_balance + deposit − withdraw` 这条恒等式，
**只有 2026-09-07 那两份夹具能验证**——整批夹具里只有它们的 `deposit` 非零
（那天是开户入金 100 万；此后再没有出入金）。

按「留最新的就够了」的直觉，这两份在 09-08 的夹具落盘之后就该被清掉。
清掉之后不会有任何东西报错，只会**永远失去验证这条关系的能力**。

> **判别力是随样本组合涨的，而删除是不可逆的。**
> 一份夹具今天没用，不等于它明天没用——它可能是唯一携带某个非零值的那份。

这条不只是规矩，它**有两道守卫**。

第一道直接盯删除：`TestCommittedFixturesStillExist` 问 git 要「提交过哪些夹具」，
逐个核它们是否还在工作树里。⚠️ 判据换过两次，两次都不是写错了，是问题问得不对：

	一版  下界 `>= 15`（实际 20 份）  → 删 2 份仍全绿，对「删除」毫无判别力
	二版  确切数，登记在 state.md     → 有牙齿，但**新增也会红**；
	                                    而探针整天在产出新证据，测试于是长期红 ——
	                                    **一个长期红的守卫会被关掉**
	三版  问 git「提交过的还在不在」   → 新增零摩擦，删除全牙齿，名单不靠人维护

第二道盯的是后果而非动作：`TestAccountIdentitiesHoldOnEveryFixture`
会统计每一类判别力各有几份样本，缺哪一类就明说哪一类在空转。
实测把 09-07 那两份移走再跑：

    --- FAIL: TestAccountIdentitiesHoldOnEveryFixture
        ⚠️ 没有一份夹具有入金 —— `static_balance = pre + deposit − withdraw` 这条恒等式空转

⚠️ 所以「删夹具」这个动作的代价是**当场可见**的，而不是几个月后才发现某条断言一直在空转。

## 9. 横着读夹具：188 份持仓截面的统计（自然日 2026-09-08 日盘）

⚠️ **这一节没有做任何新实验。** 它读的是已经躺在 `testdata/probes/` 里的
27 份夹具、188 个持仓截面 —— 那些数据此前只被**竖着**看过
（一份截面里挑几个字段），从没被**横着**统计过（一个字段在全部截面上的取值分布）。

一个「量了就算用过了」的默认，会让已经付过代价的数据白放在那里。
下面三条全部来自这一次横向统计，成本是零。

### 9.1 空仓 ⟺ `"-"`，但只在均价与保证金上

| 字段 | `"-"` | `0` | 数值 | 「空仓 ⟺ `"-"`」的反例 |
|---|---|---|---|---|
| `open_price_long` / `_short` | 144 / 185 | 0 / 0 | 44 / 3 | **0** |
| `position_price_long` / `_short` | 144 / 185 | 0 / 0 | 44 / 3 | **0** |
| `margin_long` / `_short` | 144 / 185 | 0 / 0 | 44 / 3 | **0** |
| `open_cost_long` / `_short` | 139 / 68 | 5 / 117 | 44 / 3 | **5 / 117** |
| `float_profit_long` | 139 | 11 | 38 | **5** |

前三行是干净的全称命题：**188/188 无反例**，柜台自己把「没有」与「零」分开了。

⚠️ 而后两行说明这条**不能推广**。成本与盈亏字段在空仓时给 `"-"` 还是 `0`，
是**路径依赖**的：

> 同一个合约 `SHFE.rb2610`，同样两边空仓，
> 一份截面里 `float_profit` 是 `"-"`，另一份里是 `0`。
> `SHFE.rb2701` 同样如此。

也就是说柜台的 `"-"` 在这些字段上**不是当前状态的函数**，
最可能的解释是 DIFF 的 merge-patch 语义：一个字段今天被设过值就留在数值上，
从没被设过就停在 `"-"`。本库没有「这个字段今天被设过没有」这个状态，
**复现不了，也不假装能** —— 后果是这些字段在空仓样本上**不可判**。

### 9.2 今昨拆分的成本与保证金：⚠️ 本节的原结论**已被推翻**

原文（依据交易日 20260908 的 188 份截面）：

> `open_cost_*_today` / `_his`、`position_cost_*_today` / `_his`、
> `margin_*_today` / `_his` 这 12 个字段，在 188 份截面里**全部是 0** ——
> 从不是 `"-"`，也从不是数值。
>
> ⚠️ 关键在于判别力：其中 **47 个方向确实有今仓**（`volume_*_today > 0`），
> 所以「今天没有今仓所以是 0」这个解释被否掉了。
> 作为对照，`pos_*_today` 与 `volume_*_today` 在同样这 47 个方向上**是**非零的
> —— 柜台填了手数的今昨拆分，没填金额的。

⚠️ **20260909 的日终结算一发生，上面那段就不成立了。** 而它是被
当时那条测试**当场抓到**的 —— 那条测试写下来的全部理由就是
「哪天柜台开始填了，会有动静」。修正后的事实分两条，形状不同：

    open_cost_* / margin_* 的今昨拆分   **从未**是真实数字
                                        有量那侧是 0，空的那侧是 "-"
    position_cost_* 的今昨拆分          盘中新开的仓上是 0；
                                        **经历过结算之后被填上**

一致的解释：这个拆分是在**日终结算时**算出来的（kq_facts 28/33）。

⚠️ 而「空的那一侧给 `"-"`」这个判据本身也是错的，20260909 更正（kq_facts 50）：
`"-"` 跟的是**今昨侧**（由 `PositionDateType` 定），与该方向有没有仓无关 ——
`rb2701` 结算后那几份里空头**有今仓 1 手**而 `position_cost_short_today` 照样是 `"-"`。

守卫两条：`view.TestOracleTodayHisSplit`（就是抓到这次推翻的那条，已改名）与
`fixture.TestCostSplitAbsentSideFollowsPositionDateType`。
两条断言的都是**夹具**而不是本库：柜台再变一次，还会有动静。

⚠️ 本库这边照算真值，不跟着填 0。跟着填 0 就是在**没有裁决者**的情况下选边，
而按 design.md §5，判「已知口子差异」要出处、裁决者、选边理由三样齐全，现在只有出处。
于是这 12 个字段在对拍时会红 —— **红是正确的结果**，
它说的是「两边不一样且还没人裁决」，不是「本库算错了」。

### 9.3 这三条改掉了什么

发现之前，`conformance.Field` 里只有 `Library` / `Oracle` 两个 `decimal.Decimal`,
**没有「无值」的表示法**。于是对拍侧只有两种写法，而**两种都能全绿**：

| 把 `"-"` 读成 | 后果 |
|---|---|
| `0` | 那 5 个「空仓但柜台给 0」的样本**碰巧一致**，183 个真实的「无值」被读成一致 |
| 缺失、整个跳过 | 183 个样本全部落进「未触发」，同样不报错 |

两条路互相矛盾，却都不会有任何动静。所以补了：

- `view.Absent` —— 第四种 presence，「本库建模了，结论是此处没有值」。
  ⚠️ 它与 `NotImplemented` / `NotModeled` 的区别不是措辞：**那两个是欠债，这个是结论**。
- `conformance.Field.LibraryAbsent` / `.OracleAbsent` ——
  两侧都无值按一致处理（但仍要求触发过），**一侧无值一律判失败**。
- `view.total` —— 合计不再把「无值」当 0 加进去，
  否则一次加法就能把 `Absent` 悄悄降格成 `Present`。

⚠️ 顺带记一条方法论：**一个类型里缺少某个状态的表示法，在读的时候是盲区，
在写的时候是必然的错**。这里缺的是「无值」，而它的缺失不是靠审代码发现的，
是靠把数据横着数了一遍撞出来的。

## 10. 日盘批：成交截面第一次进夹具（自然日 2026-09-08 13:2x–13:4x，交易日 20260908）

⚠️ **这一批的前提是一次格式修补，不是一次新实验。**

在此之前夹具只存账户与持仓两个截面 —— 也就是**只存了均价**。
而本库存逐笔明细的全部理由就是「均价是有损压缩」（design.md 决策 10）：

> `(2 手 @100, 1 手 @130)` 与 `(3 手 @110)` 均价相同。
> 平掉 1 手 @120 时，逐笔对冲 +20、按均价 +10，**两个结果都不会报错**。

一个为了不丢明细而做的设计，它的证据层把明结丢了。补上 `trades` 之后，
下面四条才**问得出来** —— 它们此前不是没答案，是问不出来。

补格式的当场，白名单的漂移探测器报了一句并**拒绝落盘**：

```
失败: 脱敏自检失败，**不落盘**：字段集漂移：1 个键既不在白名单也不在丢弃表里：[trades/hedge_flag]
```

⚠️ 白名单初稿是照 DIFF 文档列的，漏了 `hedge_flag`（它决定保证金率）。
**照文档列的白名单不等于实况的键集**，而这次是机制自己说出来的，不是有人想起来去数。

### 10.1 开仓均价确实是加权平均

判据设计成**输出上不可伪造**：已有 2 手 @P，再加 1 手 @Q，
均价落在 `(2P+Q)/3` —— 一个**任何单笔成交价都取不到的值**。
柜台若取首笔、末笔或最新价，都给不出这个数。

| 合约 | 已有 | 新增 | 柜台给的均价 | 加权平均预期 | 差 |
|---|---|---|---|---|---|
| `SHFE.rb2701` | 2 手 @3151 | 1 手 @3171 | 3157.666667 | 3157.666667 | 0.000000 |
| `DCE.m2701` | 2 手 @3411 | 1 手 @3423 | 3415.000000 | 3415.000000 | 0.000000 |

⚠️ 这一批同时**修好了今晚的实验 4**。原来的过夜种子是 2 手**同价**，
而平掉 1 手时三种消耗顺序（先进先出 / 后进先出 / 按比例）给出**同一个剩余均价** ——
实验 4 本来会白做，而且要到今晚才发现。加一手不同价之后：

```
剩余 {3411, 3423} → 均价 3417   先进先出消耗了 3411 那手
剩余 {3411, 3411} → 均价 3411   后进先出消耗了 3423 那手
```

⚠️ 而这条只在 `open_price` 上成立：结算会把 `position_price` 统一重置成昨结算价，
逐日盯市那条基线**认不出**是哪一手被消耗了。逐笔对冲基线永不改变，正是它的用处。

### 10.2 按额手续费：一次外推，与一条盲区

九个合约的逐笔费额，按品种分类：

| 合约 | 费额 | 昨结算价 | 费额÷昨结 | 不同成交价 |
|---|---|---|---|---|
| `SHFE.rb2610` | 0.31000 | 3100.00 | 0.0001000000 | 5 |
| `SHFE.rb2701` | 0.31580 | 3158.00 | 0.0001000000 | 5 |
| `SHFE.rb2705` | 0.31890 | 3189.00 | 0.0001000000 | 2 |
| `DCE.m2701` | 1.50000 | 3404.00 | 0.0004406580 | 4 |
| `DCE.m2703` | 1.50000 | 3338.00 | 0.0004493709 | 5 |
| `DCE.m2705` | 1.50000 | 3019.00 | 0.0004968533 | 3 |
| `SHFE.cu2701` | 27.08250 | 108330.00 | 0.0002500000 | **8** |
| `SHFE.ag2702` | 12.07125 | 16095.00 | 0.0007500000 | 2 |
| `DCE.i2701` | 7.34500 | 734.50 | 0.0100000000 | 5 |

**判据一（分类）：**

- `rb` 三个月份 → **按额**。三个**不同**费额 ÷ 三个**不同**昨结 = 同一个数。
  ⚠️ 这是一次**外推命中**：用 rb2701 标定费率，预测出 rb2610 昨结 3100、rb2705 昨结 3189，
  而这两个昨结是**独立观测**的，不参与标定。
- `m` 三个月份 → **按手固定 1.5 元**。昨结 3404/3338/3019 各不相同而费额恒定，
  于是「费额与昨结成比例」被排除。
- `ag` / `cu` / `i` 各只有一个月份 → ⚠️ **判不了**。
  单点上按手与按额给出同一个数，归进任何一类都是猜。

⚠️ 第一版判据把 `m` 的「不一致」报成了告警 —— **那是错的**：
`m` 按手收，本就不该有比例关系，「不一致」在它身上是正确答案。
一条把正确答案报成告警的判据，会训练人忽略告警。
改成三分类之后，两类**各自都是正面证据**。

**判据二（费额与成交价无关）：** `cu2701` 有八个不同成交价（108430…108630），
费额只有一个（27.0825）。九个合约无一例外。
⚠️ 这比原先「同合约一买一卖差一个 tick」强得多：两个只差一个 tick 的价，
用成交价算也可能因取整而相同 —— 八个价就没有这种解释了。

### 10.3 划出来的两条盲区

**平今费率测不出来。** 九个合约的平今费额**全部等于**它们各自的开仓费额。
也就是快期把平今费率设成与开仓相同，于是**这个维度在这个口子上没有信号**。

⚠️ 它与 §4 记的那条独立地指向同一个缺口：
DIFF 的 `quotes.commission` 是「每手手续费」的单一数值，
本来就丢掉了平今这个维度。两处不同的观察，同一个结论。

**平昨费率零观测。** 本交易日的平仓**全部**是 `CLOSETODAY`，一笔 `CLOSE` 都没有。
⚠️ 记下来是因为它决定了今晚第 8 条实验的必要性 ——
现状是「没量过」，不是「量到了等于平今」。

### 10.4 顺带补掉的一处真空

`kq.Sanitize` —— 脱敏白名单，凭据与磁盘之间那道闸 —— **此前一个单测都没有**。
仓库根上的 `fixtures_test.go` 查的是**落盘之后**的结果，只能抓已经写出去的东西，
而「先落盘再擦」正是 `runner.dump` 的注释里明确不许做的事。

补的五条测试里，破坏验证有一条值得单记：把「未登记的键进 Unclassified」
改成「未登记的键原样保留」，**改完能编译通过** ——
也就是那条静默保留的泄漏路径是真实存在的，只是此前没有任何东西会走它一遍。

## 11. 对拍闭环：从一份自足的夹具，到逐字段的判定（自然日 2026-09-08 下午）

⚠️ 这一节记的不是新实测，是把**已经在手的证据变成可机械重放的东西**。
起点是一句发现：

> 成交与行情都不在夹具里，于是「对拍」只能靠人把当时下了什么单、
> 昨结算价是多少**记在这份文档的正文里**。
> 一份要靠旁边的散文才能读懂的证据，不能被机械地重放。

补齐之后，一份夹具同时含有本库的**输入**（成交）与柜台的**输出**（持仓、账户），

### 11.3 ⚠️ 自己犯的三个错，都被守卫抓住

**一、把未实现字段填成 0 再比。** 柜台那边大量字段本来就是 0
（空仓、无期权、无冻结），于是判成一致 —— `volume_long_frozen_*`
当场就这么假通过了。**一个缺失的实现伪装成了一致**，
而这正是 `view` 包整个存在的理由所要防的。
补 `conformance.NotImplemented` 一档（不比值、不算通过）之后，
「对得上」从 44 掉到 32，那 12 个是假的。

**二、加了一档，报告里那张硬编码的档位表没同步。**
52 个字段的报告只印出 37 个的计数，剩下 15 个既不在任何一行里、
也不在逐字段行里 —— 看报告的人不会发现少了东西。
补的守卫查的不是那张表，是**合计**：印出来的计数之和必须等于字段数。
查表要求测试跟着表一起改，查合计不用。

**三、精度测试的对照是空的。** 写的是
`if 0.1+0.2 == 0.3 { t.Skip(...) }`，而两边都是无类型常量，
Go 在编译期用任意精度折叠 —— 它恒真，整条测试**恒被 skip**，
而被 skip 的正是守着精度这条最要紧性质的那一条。

## 13. ⚠️ 结算发生了，而它带来三条硬结果（自然日 2026-09-08 15:54–16:12）

**结算没有在 21:00 发生，也没有在 15:00 发生 —— 它发生在 15:54:07 与 16:09:51 之间。**

    15:54:07  watch-start-20260908-10   trading_day 20260908  pre_balance 1000000  rb 今3/昨0
    16:09:51  position-date-type-…      trading_day 20260909  pre_balance 998995   rb 今0/昨3

而进程还活着、还在等 45 分钟超时 ——
**「停了」与「没有变动」在日志上长得一模一样**，正是分段那条注释里说的事。
分段把损失限制在一段之内，但没有解决它。见 §13.4。

### 13.1 ⚠️ 大商所的持仓**没有滚**

    SHFE.rb2701   多今 0 / 多昨 3     ← 滚了
    DCE.m2701     多今 3 / 多昨 0     ← ⚠️ 一手没滚

所以「大商所还没结算」这个解释被否掉了。

> **这就是 `PositionDateType`。** 上期所 `UseHistory`，大商所 `NoUseHistory`——
> 而快期把后者实现成「持仓永远记在今仓上」。

⚠️ 对本库的直接后果：`position.Settle` 把**所有**明细标成 `Settled = true`。
在 `NoUseHistory` 合约上，柜台却仍然报 `volume_long_today`。
逐字段对拍会在这里红，而红得对 —— 本库现在缺一个「这个合约区不区分今昨」的输入。

### 13.2 平今被拒、裸平被受

新写的 `position-date-type` 实验（用挂不上的限价，被接受也不成交、随即撤单）
在 `SHFE.rb2701` 上跑出：

| 发的单 | 结果 | 柜台的话 |
|---|---|---|
| `CLOSETODAY` 1 手 | **被拒** | `平今手数超过今仓持仓量` |
| `CLOSE` 1 手 | **被接受**（挂住，随即撤） | —— |

前者证实上期所合约区分今昨。
⚠️ 后者与 roadmap 里那条设计约束**相左**：

> ⚠️ **`UseHistory` 合约上收到裸 `CLOSE` 必须报错**（roadmap v0.4.0 的验收条件）

**快期不报错，它接受裸 `CLOSE` 并自己决定消耗哪一边。**
这不推翻那条约束（本库按 CTP 建模，而 simnow_pending#1 未裁决），
但它把「裸 CLOSE 在真实柜台上会怎样」从**猜测**变成了**一个口子上的实测**。

### 13.3 ⚠️ `position_price` 是**收盘价**，不是结算价

四份结算后截面完全一致：

### 13.4 ⚠️ 盯盘漏掉了它要盯的那一刻

分段设计的注释里写着：

> 一条 WebSocket 连着六小时，断了就静默停在那里，
> 而「停了」与「没有变动」在日志上长得一模一样。

它说对了病，开错了药：**分段只把损失限制在一段之内**，

随后 45 分钟一条记录都没有 —— 日志上看起来与「一切平静」完全一样。

> **要治的是「察觉不到自己断了」，而分段治的是「断了之后多久能重来」。**
> 后者是补偿，不是诊断。

## 14. 拒绝优先级：一次得出、推翻、再得出（自然日 2026-09-09 02:0x–02:4x，交易日 20260909）

`order` 的八项校验按「拒绝优先级」排序，而那个顺序整个来自
cn-futures-rules.md §9 一张标着「**文档**」的表 —— **一次观测都没有**。

顺序错了会怎样：柜台只回一个 `last_msg`，两边都判「拒绝」，
⚠️ **差异不会以失败的形式出现**。

### 第一轮：得出了一个相反的结论，并真的改了代码

在 SHFE.ag2702 上构造「同时违反两项」的单子，比对柜台原话：

    价内的非整数倍价 13009.3333  →「下单价格不是价格单位的整倍数」
    越涨停的非整数倍价 20489.7   →「已撤单报单被拒绝价格超出涨停板」

读作「越界优先于整数倍」，与文档表相反。于是把 `order.CheckPriceLimit`
排到了 `order.CheckPriceTick` 前面。

⚠️ **对调之后全套测试照样绿** —— 八项的相对顺序此前是一段**没有任何守卫**的
语义，而它在代码里长得和被守卫的部分一模一样。

### 第二轮：同一批构造，答案反过来了

把构造修干净（越界改用 `涨停价 + 10×tick`，仍然对齐 tick）之后再跑：

    越界 + 零头 1/3 个 tick  →「下单价格不是价格单位的整倍数」

**与第一轮相反。** 两轮之间同时变了两样：价格的零头（0.7 对 1/3）
与所处时段（盘中对收盘后）。⚠️ 一次变两个自变量的实验问不出是哪一个在起作用，
而两轮各自的日志都完全正常、各自都打印出了一个明确的结论。

### 第三轮：只扫一维，答案出来了

固定合约、固定时刻、固定越界幅度，**只改零头**：

| 零头（单位：一个 tick） | 柜台 |
|---|---|
| 0 | 报涨跌停 |
| 1/10 | 报「不是整数倍」 |
| 1/3 | 报「不是整数倍」 |
| 1/2 | 报涨跌停 |
| 7/10 | 报涨跌停 |
| 9/10 | 报涨跌停 |

再把同一组零头搬到**价内**（买在跌停附近，接受了也不会成交）：
1/10 被拒，而 1/2、7/10、9/10 **被接受挂上去了**，
委托记录里还留着那个带零头的价（`limit_price=13009.9`）。

⇒ **快期只在零头 < 半个 tick 时才认为「不是整数倍」。**
换 DCE.i2701（tick=0.5）再扫一遍，边界同样落在半个 tick 上 ——
**随 tick 缩放**，不是某个绝对数。

于是第一轮那笔 20489.7（零头 0.7）**根本不是「同时违反两项」**，
它只违反了涨跌停。文档表是对的，代码改回去。

### ⚠️ 零层为什么没拦住

第二轮已经给实验补过一层「违规真的构造出来了吗」的当场核对，
而它**照样放过了**第一轮那种单子 —— 因为它用的是**本库的**判据
（`|price/tick - round(price/tick)| > 容差`），而分歧恰恰在判据本身。

> **一个用自己的定义去核对自己的守卫，对「定义分歧」没有判别力。**

修法是把 `offTick` 整个换成**柜台的**判据（零头 < 半个 tick），
并在两端都钉住：下界（容差随 tick 缩放）与上界（≥ 半 tick 时柜台收下）。
上界此前**根本不存在**，而那正是错的根子。

### 顺带撞出来的两件事

**一、落盘时的采样判据漏了一类合约来源。** 挑哪些合约的行情进夹具，
判据原本是「持仓里出现过、或成交里出现过」。而 reject 系列实验的形状是
**只下单、全被拒、没有持仓也没有成交** —— 于是
`exp-reject-tick-vs-limit-20260909-3.json` 的**行情段整个是空的**。

⚠️ 后果不是报错，是下游对拍**静默跳过**那一份：
「跳过了一份」与「比过了一份且一致」在汇总行里长得一模一样。
判据补上委托那一支之后重跑得到 `-4`，那一份有行情。原件留档不重制 ——
它记的是那一刻的账户，重制出来的是另一个时刻。
守卫 `TestFixtureQuotesCoverOrderedSymbols`（棘轮，只许减少）。

**二、开仓挂单的冻结保证金第一次有了样本。** 那笔被收下的挂单让账户
出现了非零的 `frozen_margin`，两个合约各一次：

    SHFE.ag2702  昨结 16262 × 乘数 15  × 22% = 53664.6
    DCE.i2701    昨结 740   × 乘数 100 × 11% = 8140

⚠️ 两笔的**报单价**（13009.9 / 673.95）都远低于昨结算价，按报单价会算出
42932.67 与 7413.45 —— 于是「按昨结算价」与「按报单价」被分得干干净净，
**不是一次同值的巧合**。`frozenTotals` 里原本那句「没见过的情形不猜」
到此为止（kq_facts 46）。

### 三条入库的守卫

    TestPriceTickBeforePriceLimit         常量顺序，注释里写着翻案经过
    TestRejectPriorityFromFixtures        从夹具重算三组原话，逐字比
    TestCounterTickToleranceIsHalfATick   半 tick 这条边界，三组样本都要有

### 复跑

    cd cmd/oracle
    go run . probe -env ../../.env         -specs ../../testdata/refdata/specs-20260908.json         -exp reject-tick-vs-limit -symbols SHFE.ag2702

⚠️ `-specs` **没有默认值**：免费行情**不下发** `price_tick`，`q.PriceTick` 恒为 0，
而 0 是个看起来完全合理的数 —— 拿它构造「不是整数倍」，构造出来的价格是整数倍，
于是那一项**根本没被违反**，实验却照样跑完。

## 15. 柜台还有第二条回话通道（自然日 2026-09-09 04:0x，交易日 20260909）

问的本是「合约不可交易这一项排在哪」。做法：拿一个**不存在的合约**
（同品种、一个不会有的月份 `SHFE.ag9912`）下单，与真实合约上的同一个
偏离整数倍价对比。

### 第一次跑：柜台「没反应」

    真实合约 · 偏离整数倍   FINISHED  下单价格不是价格单位的整倍数
    假合约   · 整数倍       未在 15s 内到终态(status=)   （空）
    假合约   · 偏离整数倍   未在 15s 内到终态(status=)   （空）

假合约那两笔**连委托记录都没有**：`status` 与 `last_msg` 全空。
⚠️ 这与「单子还挂着」长得一模一样 —— 一个只读委托记录的实验，
在这里只能得出「柜台没反应」这个错误结论。

### 第二次跑：把 `notify` 也打出来

DIFF 除了截面还有一条 `notify` 通道，而**本仓库此前所有的拒因实验
都只读委托记录**。打开它之后：

    真实合约 · 偏离整数倍   code=412  下单,已被服务器拒绝, 原因:下单价格不是价格单位的整倍数
    假合约   · 整数倍       code=311  您下单的合约SHFE.ag9912不存在
    假合约   · 偏离整数倍   code=311  您下单的合约SHFE.ag9912不存在

⇒ 第三笔回的是 311 不是 412 ⇒ **合约排在价格类校验之前**，与 §9 一致。
拒绝优先级又多判出一对，计数与清单见 state.md 的 `reject_priority_measured`。

### 两条比位次更重要的收获

**一、通知带数值码。** ⚠️ simnow_pending#5 原先写着「快期模拟给的是中文文案，
不能拿来填」—— **那句话不准**。结论没变（311/412 是**天勤自己的**码，
不是 CTP 的 `ErrorID`），但理由要说准：不是「没有码」，是「码不是那一套」。

> **一个理由说错了的待办，会让下一个人去找一个本来就不存在的东西。**

**二、归因要挑一条「三笔单都有」的通道。** 这一轮如果拿 `last_msg` 去比，
比的是「一句话」和「两个空串」，而空串什么都不是。改用 notify 的码之后
三笔都有值，比对才成立。

### 通知进夹具，但**不收文案**

⚠️ `type` / `level` / `code` 收；`content` **一个字都不收**。
白名单的保护方式是「逐个字段点名」，而 content 是服务器写的自由文本 ——
一个自由文本字段从原理上就不在白名单的保护范围内：谁也不能担保
下一条通知里不会出现账号或姓名。仓库是公开的，泄漏不可逆。

⚠️ 这是个**要人来定的取舍**，不该由一次无人值守的实现顺手改掉。
数值码足够做拒因对拍；文案由人工看过之后写进 §9 的表。
守卫 `TestNotifyCodesAreKnown`：出现没登记过的码就红，
逼人去看那一条是什么 —— 一个没人看过的码与一个看过并判定为无关的码，
在数据里长得一模一样。
