## 0. 一句话：它和加密货币衍生品到底差在哪

差在**结算**。

OKX 那类交易所是**连续记账**：标记价一变，未实现盈亏、保证金率、强平价立刻跟着变，
一天二十四小时是同一个连续函数。

中国期货是**逐日盯市**：一天之内是一套账（盯着最新价看浮盈、保证金基本不动），
收盘后交易所公布**结算价**，用它把当天的浮盈浮亏**兑现成现金**、把保证金**重算一遍**、
把**今仓变成昨仓**，然后第二天在新的基线上重新开始。

于是本库的核心不是「行情 → 指标」，而是**一条以交易日为单位的状态机**：

```
盘中：成交进来 → 更新持仓与冻结 → 浮动盈亏随最新价变
                      ↓
日终：结算价到位 → 逐日盯市 → 兑现盈亏 → 重算保证金 → 今仓转昨仓 → 出结算单
                      ↓
次日：昨结算价成为新基线
```

**照搬加密货币的连续模型，每一天收盘都会错一次，而且错得很像对的。**

## 2. 字段语义陷阱

CTP 的命名有几处会主动误导人，先钉死：

| 字段 | 直觉 | 实际 |
|---|---|---|
| `TradingAccount.Balance` | 静态结存 | 盘中是**动态权益**（已含 `PositionProfit`）。日终结算后才等于结存 |
| `TradingAccount.PreBalance` | 昨天的余额 | **上一交易日结算后的结存**，是今天一切计算的基线 |
| `InvestorPosition.Position` | 持仓量 | 是今昨两笔的合计。`YdPosition` 是**昨日结算后**的量，盘中平昨会减 `Position` 而**不减** `YdPosition` |
| `InvestorPosition.PositionCost` | 开仓成本 | 逐日盯市口径的成本，**每日结算后按结算价重置**。要原始开仓成本看 `OpenCost` |
| `InvestorPosition.UseMargin` | 保证金 | **期货公司**口径。交易所口径在 `ExchangeMargin`，两者一般不等 |
| `CloseProfit` | 平仓盈亏 | 是 `CloseProfitByDate`（逐日盯市）。逐笔对冲口径在 `CloseProfitByTrade`，**同时存在** |
| `TradingDay` | 日期 | **交易日**，不是自然日。夜盘 21:00 之后的 `TradingDay` 是**下一个**交易日 |

最后一条最容易出事，单独展开。

### ⚠️ 截面字段数：文档说的和柜台给的对不上（**实测（快期模拟·取值）**）

2026-09-07 实测，两处都比 DIFF 文档列的多：

| 截面 | 文档 | 实测 | 多出来的 |
|---|---|---|---|
| 账户 | 18 | **23** | `ctp_available` `ctp_balance` `market_value` `pre_option_market_value` `user_id` |
| 持仓 | 28 | **54** | 20 个（另有 6 个文档列了但需持仓才出现） |

持仓多出来的那 20 个**不是噪声，是结构性证据**：

```
margin_long_today / margin_long_his          保证金按今昨分开
open_cost_long_today / open_cost_long_his    开仓成本按今昨分开
position_cost_long_today / _his              持仓成本按今昨分开
volume_long_yd                               昨仓量的另一口径，与 volume_long_his 并存
```

⚠️ **柜台把 margin / open_cost / position_cost 三样都按今昨拆开**，
这正是逐日盯市要求的两条基线（昨仓以昨结算价、今仓以开仓价）在柜台侧的形态。
本库的 `position` 包必须同构，不能只存合计。

> ⚠️ **上面说的是「协议里有这些字段」，不是「柜台把它们填上」** ——
> 原文写的是「拆开**存**」，而 20260909 实测下来三样的行为并不一样
> （state.md 的 `kq_facts` 28/33/50）：
>
>     open_cost_* / margin_* 的今昨拆分   **从未**是真实数字
>     position_cost_* 的今昨拆分          **经历过结算之后**才被填上，
>                                         由 PositionDateType 决定写哪一侧，
>                                         另一侧给 "-"（**与有没有仓无关**）
>
> ⚠️ 「本库必须同构」这个结论**不受影响** —— 它的理由是逐日盯市本身要求
> 两条基线，不是「柜台填了所以我们也要填」。两个理由长得像，而**只有前一个
> 在柜台不填的时候仍然成立**。
> 守卫：`view.TestOracleTodayHisSplit`、
> `fixture.TestCostSplitAbsentSideFollowsPositionDateType`。

⚠️ `volume_long_yd` 与 `volume_long_his` **并存且含义未定**——列为新的待实测项。
（⚠️ 快期这一侧已经测出来了，见 `kq_facts` 27 与本页 §13 第 7 条；
仍留在待实测，因为只有一个来源。）

这 20 个字段是**被字段集断言自动抓出来的**，不是靠人去数：
夹具生成时断言「收到的字段集 ⊆ 已知字段集」，多出来即判未分类并**拒绝落盘**。
它在第一次真实建仓时就报了警。

### ⚠️ 交易日 ≠ 自然日（**文档**）

夜盘（21:00 起）属于**下一个交易日**。周五夜盘属于**下周一**。

这意味着：

- 周五 21:00 开的仓，在**周一**日盘看来是「昨仓」还是「今仓」？——是**今仓**，
  因为它和周一日盘属于同一个交易日，中间**没有结算**
- 一个交易日可能横跨三个自然日（周五夜盘 → 周六凌晨 → 周一日盘）
- 节假日前的夜盘不开；长假前后的交易日映射必须查**交易日历**，不能用「下一个工作日」推

**本库不推算交易日，它由日历数据给出。** 用工作日近似会在每个长假前后错一次，
而错的那几天恰好是保证金上调、风险最高的时候。

#### ⚠️ 本仓库怎么把这两者**写**开（2026-09-09 补：此前只有实践，没有约定）

    交易日   `20260910`      无分隔符
    自然日   `2026-09-09`    带横杠

⚠️ **补这一句的起因是它差点被用错**：2026-09-09 傍晚结算之后，交易日滚到
`20260910`，两者**正好差一天**；而当时要给一条方法论署日期，两个数都「看起来对」。

去核仓库怎么规定的，结果是：

    概念   写清楚了 —— 就是上面这一节
    格式   ⚠️ **一个字都没写过**
    实际   docs 里交易日式 143 处、自然日式 148 处，**291 处靠每个人每次都记得**

> ⚠️ 一条被 291 处一致遵守、却从未被写下来的约定，与一条不存在的约定
> 在**新来的人**面前是同一回事 —— 而它每天都在被使用。

⚠️ **守卫只兜住一半，另一半写出来**：

    说了角色词的     「交易日」后面跟了**带横杠**的日期，
                     或「自然日」后面跟了**无分隔符**的日期
                     → ⚠️ **机械可判**，守卫 `TestDateRoleMatchesFormat`（现状错配 0，是个棘轮）
    光秃秃的日期     前后没有角色词，只有一个 `20260910` 或 `2026-09-09`
                     → **抓不到**，靠人

⚠️ 而**引发这条约定的那个错，恰好落在抓不到的那一半里**：
一句「双方在 20260910 的排查中确立」——那天的自然日是 2026-09-09，
句子里没有角色词，两条守卫都不匹配。

> **判据是按「能机械化的形状」设计的，不是按「实际发生的那个错」设计的。**

⚠️ **还有一条限制，是这条守卫刚上线就自己撞出来的**：它**分不开**
「示范一个错误写法」与「犯那个错」。上面这两行原本写的是具体的反例字样，
守卫当场把文档自己报成了违规。现在改成描述而不是举例 ——
**代价是这一段不如原来直观，而那就是这条守卫的价格。**

⚠️ 所以别把它读成「日期格式这块已经保住了」——
**一个只守住简单一半的守卫，比没有守卫更容易让人放松。**

## 3. 合约规格

来自 `CThostFtdcInstrumentField`（35 字段），本库用到的：

| 字段 | 用途 |
|---|---|
| `VolumeMultiple` | 合约乘数。**所有金额都要乘它**，漏乘会得到一个量级正确到肉眼看不出的错值 |
| `PriceTick` | 最小变动价位。报单校验与价格取整 |
| `LongMarginRatio` / `ShortMarginRatio` | 多空保证金率**可以不等** |
| `MaxMarginSideAlgorithm` | 是否单向大边，见 §6 |
| `PositionDateType` | `UseHistory` 区分今昨仓 / `NoUseHistory` 不区分，见 §4 |
| `PositionType` | `Net` 净持仓 / `Gross` 综合持仓（可同时持有多空），见 §4 |
| `ProductClass` | 期货 / 期权 / 组合。v1.0 只做期货 |
| `ExpireDate` `StartDelivDate` `EndDelivDate` | 交割相关，见 §11 |
| `IsTrading` `InstLifePhase` | 合约是否可交易 |

### 合约代码的大小写与月份位数（**文档**）

| 交易所 | 形态 | 例 |
|---|---|---|
| SHFE / INE / DCE / GFEX | 小写 + 四位年月 | `rb2610` `sc2611` `m2701` `si2612` |
| CZCE | **大写 + 三位年月** | `AP610` `TA701` |
| CFFEX | 大写 + 四位年月 | `IF2609` `T2612` |

跨十年的历史回测必须由外部给出年代，本库**不猜**。

## 4. 持仓模型

### 三个正交的维度

一个持仓由 `(合约, 买卖方向, 投机套保标志)` 唯一确定，再按今昨拆分：

```
PosiDirection   Net / Long / Short
HedgeFlag       Speculation 投机 / Arbitrage 套利 / Hedge 套保
PositionDate    Today 今仓 / History 昨仓
```

⚠️ **`HedgeFlag` 不是标签，它决定保证金率。** 套保持仓的保证金率通常低于投机。
把套保仓按投机记账会**高估**保证金占用，进而低估可用资金——看起来「保守」，
实际上会让回测里本可以开的仓开不出来，策略被无声地阉割。

v1.0 只做**投机**，套保与套利留到后续版本，理由是它们需要交易所的套保额度审批数据，
回测里拿不到。**但字段从第一天就带上**，不留后患。

### 今仓与昨仓（**文档**，逐合约由 `PositionDateType` 决定）

`PositionDateType = UseHistory` 的合约（典型：SHFE、INE、CFFEX）：

- 持仓**分**今昨两笔，报单必须显式声明「平今」或「平昨」
- ✅ **实测（快期模拟·语义，2026-09-07，SHFE.rb2701）**：空仓时报普通「平仓」，柜台答
  `平昨手数超过昨仓持仓量` —— 即 `CLOSE` 在此类合约上**被解释为平昨**，
  不是由柜台择优。见 §9 拒因表。
  ⚠️ **但这条证据来自快期模拟，按本文表头的坐标表，那一档明确标着「不等于真实柜台」。**
  所以本库的处理是：**收到裸 `CLOSE` 时报错，而不是按平昨处理**，
  直到 SimNow 复核（那正是「权威裁决」这个角色的定义）。
  显式声明本来就是要求，报错的代价近乎为零，而猜错的代价是**平错一边的仓**。
  ⚠️ **「没测出来」和「测出来是平昨」，在代码里长得一模一样**——
  与「零值不是安全的默认」是同一条。
- ✅ **再次实测且样本强得多（20260909 夜盘，`SHFE.rb2701` 多今 1/多昨 3）**：同一个截面上发 `CLOSETODAY` 冻 `volume_long_frozen_today`、发 `CLOSE` 冻 `volume_long_frozen_his`；而在**只有今仓**的空头方向上发 `CLOSE` 仍被拒（原话同上）。
  ⚠️ 上一次的样本只有昨仓，「解释为平昨」与「择优挑了唯一有量的那边」分不开；今昨并存才把两者分开。**结论不变，但这次它是被分开过的。**
  ⚠️ 本库仍**不改**：裸 `CLOSE` 照样报错，理由一字未动 —— 证据来自快期模拟，而按表头坐标那一档标着「不等于真实柜台」。见 [state.md](./state.md) kq_facts 32。

`PositionDateType = NoUseHistory` 的合约（典型：DCE、CZCE）：

- 持仓**不分**今昨，报普通「平仓」即可
- ⚠️ **但手续费仍可能区分平今**（`CloseTodayRatioByMoney` / `CloseTodayRatioByVolume` 有值）。
  柜台在计费时按今昨自动拆分，而持仓查询里看不到这个拆分。
  **「持仓不分今昨」不等于「费用不分今昨」**，这两件事各由一个字段控制

**待实测**：`NoUseHistory` 的合约上，柜台按什么顺序消耗今昨仓来计费？候选：

1. 先平昨、后平今（对客户有利，平今费率通常更高）
2. 先平今、后平昨
3. 按开仓时间先进先出

判别实验：同一合约上先建昨仓（隔日），次日再开今仓，然后平掉**少于**昨仓量的手数
（平满了三种顺序同值，测不出来）。**同时看两个字段**：`Commission` 与
`CloseProfitByDate`。三个候选在这一笔上给出三组不同的数。

⚠️ **这条的影响面不止手续费。** 按 §5 的公式，逐日盯市的平仓盈亏
「平昨用昨结算价、平今用开仓价」——**消耗顺序换一个，基线跟着换**。
`CloseProfitByDate` 上的差通常比手续费**大一个量级**，反而是更好的判别字段。
它阻塞的是 `fee` + `pnl` + `account` 三个包，不是两个。

### 净持仓与综合持仓（**文档**）

`PositionType = Gross` 时，同一合约可同时持有多头与空头（**双向持仓**），
两边各自占用保证金（除非该品种走单向大边，见 §6）。
`PositionType = Net` 时只有净头寸。

国内商品期货绝大多数是 `Gross`。**双向持仓不会自动对冲**——这是与「净持仓」
直觉最大的分歧点，也是很多回测把保证金算少一半的原因。

## 5. 盈亏：两套口径同时存在

`CThostFtdcInvestorPositionField` 里 `CloseProfitByDate` 与 `CloseProfitByTrade`
并列，`InvestorPositionDetail` 里 `PositionProfitByDate` 与 `PositionProfitByTrade`
并列。**这不是冗余，是两种会计口径。**

### 逐日盯市（ByDate）——资金结算走这一套（**文档**）

基线是**昨结算价**，不是开仓价。

```
持仓盈亏 = Σ 昨仓量 × (今结算价 − 昨结算价) × 乘数 × 方向
         + Σ 今仓量 × (今结算价 − 开仓价)   × 乘数 × 方向

平仓盈亏 = Σ 平昨量 × (平仓价   − 昨结算价) × 乘数 × 方向
         + Σ 平今量 × (平仓价   − 开仓价)   × 乘数 × 方向

方向：多头 +1，空头 −1
```

关键在于**昨仓的成本基线是昨结算价**。持有三个月的仓位，它的「开仓价」在逐日盯市
口径里早就不存在了——每天结算都把它重置一次。

### 逐笔对冲（ByTrade）——客户看的另一套（**文档**）

基线是**原始成交价**，跨结算日不重置：

```
平仓盈亏 = Σ (平仓价 − 该笔的开仓价) × 量 × 乘数 × 方向
```

这一套需要**逐笔持仓明细**（`InvestorPositionDetail`），因为它要知道每一笔是哪次开的。
所以本库的持仓状态机**必须保留逐笔明细**，不能只存一个均价——存了均价就再也算不回来。

⚠️ **这是一条第一天就要定死的结构决策。** 事后补明细等于把历史丢了：
均价是有损压缩，`(2 手 @100, 1 手 @130)` 与 `(3 手 @110)` 的均价相同、
逐笔对冲盈亏不同，而且**两者都不会报错**。

### 当日盈亏

```
当日盈亏 = 平仓盈亏 + 持仓盈亏          （均为逐日盯市口径）
```

### ⚠️ 盘中的 `PositionProfit` 用哪个价（**待实测**；今仓的基线已实测，判别力仍不足）

日终用结算价，这没有疑问。盘中呢？候选：

1. 最新成交价
2. 昨结算价（即盘中持仓盈亏只反映今仓、昨仓恒为零）
3. 柜台配置项，各家不同

判别实验：持一手昨仓，盘中记录最新价与 `PositionProfit`，
候选 1 会随行情连续变动，候选 2 恒为零。一次查询即可分开。

**交易日 20260908 的夜盘量到的（快期模拟·取值），以及它为什么还不够：**

今仓上，持仓截面给出 `position_price_long == open_price_long`（3149 对 3149），
`position_profit == float_profit`（八个采样点全部相等），
两者都随最新价连续变动。这与本库 `pnl` 包的模型一致：
**逐日盯市下今仓的基线就是开仓价。**

⚠️ **但这一条对上面三个候选没有判别力。** 今仓的基线本来就是开仓价，
无论盘中标记价取最新价还是昨结算价，`position_profit` 都会随行情动。
真正能分开候选 1 与候选 2 的是**昨仓**：候选 2 下昨仓的持仓盈亏恒为零。
所以这一栏仍是**待实测**，要等过夜种子结算之后（实验 2）。

⚠️ 写下「今仓已验证」而不写「它证不了候选之间的差别」，
就会让人以为这一格已经填上了。**阴性结果不能当阳性用**，
而「有判别力的观测」与「有数字的观测」是两回事。

这条不确定会传染到**风险度**，进而传染到**追保与强平判据**——即整个风控链路的入口。
在实测之前，本库按候选 1 建模并在文档与代码里标注。

## 6. 保证金

### 两层：交易所与期货公司（**文档**）

```
交易所保证金 ExchangeMargin = Σ 持仓量 × 价格 × 乘数 × 交易所保证金率
期货公司保证金 UseMargin    = Σ 持仓量 × 价格 × 乘数 × 公司保证金率
公司保证金率 = 交易所保证金率 + 加收比例        （加收由期货公司设定，≥ 0）
```

风险度、可用资金、追保、强平**全部用公司口径**。交易所口径只在会员层面有意义，
但 CTP 两个都返回，对拍要两个都对上。

回测场景下使用者通常拿不到某家期货公司的加收比例，因此本库把它做成**可配置的加收**，
默认 0（即等于交易所口径）并在文档里写明这会**低估**保证金占用。

### 保证金率的两种形态

`LongMarginRatioByMoney` / `LongMarginRatioByVolume` —— **按金额**与**按手数**并存，
两者相加：

```
保证金 = 持仓量 × 价格 × 乘数 × ByMoney + 持仓量 × ByVolume
```

国内商品期货基本只用 ByMoney，ByVolume 多为 0。但公式要写全，
因为**一个恒为 0 的加项不会暴露自己被漏掉了**。

**交易日 20260908 的夜盘实测（快期模拟·取值）：保证金率分品种，不是全局统一值。**

| 合约 | 昨结算价 | 乘数 | 每手保证金 | 昨结基准反解 |
|---|---|---|---|---|
| `SHFE.rb2610` | 3100 | 10 | 2170.00 | `0.07000000` |
| `SHFE.rb2705` | 3189 | 10 | 2232.30 | `0.07000000` |
| `DCE.m2703` | 3338 | 10 | 2336.60 | `0.07000000` |
| `DCE.m2705` | 3019 | 10 | 2113.30 | `0.07000000` |
| `DCE.i2701` | 734.5 | 100 | 8079.50 | `0.11000000` |
| `SHFE.cu2701` | 108330 | 5 | 59581.50 | `0.11000000` |
| `SHFE.ag2702` | 16095 | 15 | 53113.50 | `0.22000000` |

乘数由 `open_cost / (open_price × volume)` 反解，不查表也不假设位数。

⚠️ **这张表我一度得出过相反的结论。** 最先量的三个合约是 `rb2701` / `rb2610` / `m2701`，
三个都是 7%，我据此写下「快期用的是全局统一简化费率，因此不能当保证金率的对拍口子」。
那是错的：**那三个样本恰好全落在同一档费率上，没有任何判别力**，
「复核」只是把同一次观测做了三遍。换上 `i` 与 `cu` 之后 11% 立刻出现。
判别力必须先于结论被证明，这条教训见 [silent-risks.md](./silent-risks.md)。

### 「价格」是哪个价（**实测（快期模拟·取值）**；今仓已定，昨仓仍待测）

这是本库与加密货币模型差别最大的一条，也是最容易想当然的一条。候选：

1. **昨仓用昨结算价，今仓用开仓价**（结算基线一致，最符合逐日盯市的内在逻辑）
2. 昨仓与今仓都用昨结算价
3. 全部用最新成交价（连续重估，加密货币的形态）
4. 全部用今结算价（只有日终才成立，盘中拿不到）

**交易日 20260908 的夜盘实测：今仓用昨结算价。** 候选 1 与候选 3 均被排除。

四条证据，各自的失败方向不同——任一条单独成立都可能是巧合，四条一起不像：

| 证据 | 它排除了谁 |
|---|---|
| 六个合约横跨两个交易所，用昨结算价反解隐含费率得到精确的 `0.07000000` / `0.11000000`；用最新价反解得到 `0.06960381` / `0.10940420` / `0.10979729` 这样各不相同的脏数 | 候选 3 |
| 同一合约上多头成交在 3149、空头成交在 3148，两边 `margin` **完全相同**（各 2210.60） | 候选 1（今仓用开仓价） |
| 持仓不动，最新价在 3149–3151 之间走过 8 个采样点，`margin` 全程锁死 2210.60；若按最新价算应在 2204.3–2205.7 之间浮动 | 候选 3，与第一条彼此独立 |
| 过夜种子两条腿相对昨结算价**方向相反**（rb2701 成交 3151 / 昨结 3158，m2701 成交 3411 / 昨结 3404），`margin` 仍分别精确等于昨结基准值 | 把差值符号写反的实现 |

⚠️ **这一条只答了今仓。** 昨仓要等种子过夜结算之后才测得到（实验 1b）。
在那之前**不得**把结论写成「今昨都用昨结算价」——那正是候选 2，它一次也没被测过。
今仓的结论对候选 1 与候选 2 的**昨仓部分**没有任何判别力。

⚠️ **口子的性质要一并记住。** 这测的是**快期模拟怎么实现**，不是交易所规则本身。

⚠️ **而且这条问题的提法本身可能就不对：它也许根本没有唯一答案。**

CTP 里有 `MarginPriceType`（保证金价格类型），本机 `goctp@v1.10.17` 实测：

| 取值 | 标识符 | 源码里的中文注释 |
|---|---|---|
| `'1'` | `PreSettlementPrice` | 昨结算价 |
| `'2'` | `SettlementPrice` | ⚠️ **最新价** |
| `'3'` | `AveragePrice` | 成交均价 |
| `'4'` | `OpenPrice` | 开仓价 |

**一个可配置的枚举字段，四个取值几乎就是上面的候选集。** 它的存在不是「规则如此」的
佐证，恰恰相反——它是「**不存在唯一全局答案**」的证据。

⚠️ 三点必须一并记下，否则这段会被读成比它更强的东西：

1. **`'2'` 的标识符与注释在源码内部自相矛盾**：标识符写 `SettlementPrice`（今结算价），
   中文注释写「最新价」。**我无法从这一份源码判定哪个对。**
2. **`'3'` 成交均价是上面候选表里从来没有的一项。**
3. **映射不是 1:1**：候选 1（今仓用开仓价、昨仓用昨结算价）是**复合**的，
   而 `MarginPriceType` 是单选。要么今昨两腿各自适用不同规则，要么候选 1
   本身不是 CTP 的形状。**这一点我没有证据。**

⚠️ **粒度要看清，它决定这个配置该放在哪一层。** 实测三个字段各自挂在哪个结构体上：

| 字段 | 所属结构体 | 键 | 粒度 |
|---|---|---|---|
| `MarginPriceType` | `CThostFtdcBrokerTradingParamsField` | BrokerID + InvestorID + CurrencyID + AccountID | **经纪商 / 账户级** |
| `PositionDateType` | `CThostFtdcProductField` / `CThostFtdcInstrumentField` | 品种 / 合约 | 逐品种 / 逐合约 |
| `MaxMarginSideAlgorithm` | `CThostFtdcInstrumentField` | 合约 | 逐合约 |

所以 `MarginPriceType` **与后两个不是同一类**：它不该进按合约键控的 `refdata`，
而属于账户 / 经纪商参数。⚠️ 「都是可配置的」不等于「配置在同一层」——
按错误的粒度存一个配置，等于给它安了一个永远查不对的键。

`margin` 包的 `PriceBasis` 参数保持不变；在这个框定下它**更该是必填**，
只是它的值将来应当来自柜台参数，不是调用方拍一个。

SimNow / 真实柜台的复核仍然欠着，见 [state.md](./state.md) 的 `simnow_pending`。

`margin` 包的 `PriceBasis` 参数保留不变：它仍是显式的、零值报错的参数，
只是现在有了一个有实测支撑的取值。

### ⚠️ 单向大边（**文档**；快期模拟上**未启用**，规则本身仍待实测，高风险）

`MaxMarginSideAlgorithm` 为「是」的品种，同时持有多空时**只收较大的一边**：

```
保证金 = max(多头保证金合计, 空头保证金合计)
```

⚠️ **合并的范围是「品种」还是「合约」，决定了结果差多少倍。** 交易所规则按**品种**
（同一品种的所有月份合约合并算大边），而 `MaxMarginSideAlgorithm` 挂在**合约**上。

这是一个典型的静默错误形态：**单合约双向持仓时，按合约合并与按品种合并给出同一个数**。
只有在「同品种多个月份、且多空分布在不同月份」时两者才分开——而这种持仓在测试样本里
不常见，在真实的跨期套利里却是常态。

判别实验：在同一品种的两个不同月份合约上分别建多头与空头，看 `UseMargin` 合计
是等于 `max(多, 空)` 还是 `多 + 空`。**必须用两个不同月份，单合约测不出来。**

**交易日 20260908 的夜盘实测（快期模拟·取值）：这个口子上单向大边根本没启用。**

| 样本 | 只有多头腿 | 只有空头腿 | 两腿齐备 | 之和 | 较大者 |
|---|---|---|---|---|---|
| `rb2701` 多 + `rb2610` 空（跨合约） | 2210.60 | 2170.00 | **4380.60** | 4380.60 | 2210.60 |
| `rb2701` 多 + `rb2701` 空（同合约） | 2210.60 | 2210.60 | **4421.20** | 4421.20 | 2210.60 |

⚠️ **这不是「合并范围 = 合约」。** 同合约双向那一行才是关键：
若大边启用而只按合约合并，同合约双向就该收较大者 2210.60，实测是两条腿相加。
两行合起来说明的是**大边这条规则在快期模拟上不存在**。

⚠️ 于是这条实验的产出不是规则的答案，而是**口子的边界**：
`MaxMarginSideAlgorithm` 的合并范围**在快期模拟上测不出来**，
因为被测对象不实现它。它转入 SimNow / 真实柜台待测，见 [state.md](./state.md)。
`margin` 包的 `SideScope` 参数因此**保持零值报错不变**——
一条测不出来的规则，不该因为「量过了」就获得一个默认值。

⚠️ 判据本身也修过一次。原判据写的是「两腿保证金相等则判据不成立」，那是错的：
`之和 == 较大者` 的充要条件是**某一边为 0**，两边都等于 X 时之和 2X、较大者 X，
判别力完好。上表第二行正是两腿精确相等的样本，它照样分得开。
而原判据真正会触发的场合是「有一条腿没建上」，却会去报「样本选得不好」——
**一个指向未经验证的原因的错误信息**。

⚠️ 另外，最初的判据拿的是**持仓字段之和**与账户 `margin` 比。那是同义反复：
若大边在持仓字段上就已生效，「账户合计 = 两腿字段之和」会恒成立。
现在改成三次**账户级**采样（只多 / 两腿 / 只空），不依赖持仓字段怎么报。

（这条与本项目的参照仓库 `okx-position-simulator-go` 踩过的坑同构：那边是
「全仓按 instFamily 合并查档」，单仓位时三种解释同值，多仓位才分开。）

### 交割月保证金递增（**文档**）

临近交割，各交易所按阶梯提高保证金率（如「交割月前一个月上旬 / 中旬 / 下旬」三档，
进入交割月再提一档）。这是**规则数据**，不是公式——本库从规则数据里查，
`refdata` 提供按「距交割的天数或旬」查率的接口。

## 7. 手续费

`CThostFtdcInstrumentCommissionRateField` 给六个率，两两一组：

```
开仓    OpenRatioByMoney       OpenRatioByVolume
平昨    CloseRatioByMoney      CloseRatioByVolume
平今    CloseTodayRatioByMoney CloseTodayRatioByVolume

单笔手续费 = 成交量 × 成交价 × 乘数 × ByMoney + 成交量 × ByVolume
```

同一品种通常只用其中一种形态（要么按金额，要么按手数），另一种为 0。
**两项都要算并相加**，理由同 §6：恒为 0 的加项不会暴露自己被漏掉。

⚠️ **平今费率可以远高于平昨**，也可以为 0（部分品种免平今）。日内策略的手续费
几乎全部落在平今上——把平今当平昨算，日内策略的回测收益会系统性偏高，
且偏高的幅度正比于交易频率，**频率越高的策略被高估得越多**。

### 快期模拟实测到的收法（**实测（快期模拟·取值）**）

交易日 20260908 的夜盘，六个合约横跨两个交易所：

| 合约 | 昨结算价 | 乘数 | 开仓费 | 平今费 | 收法 |
|---|---|---|---|---|---|
| `DCE.m2703` | 3338 | 10 | 1.5000 | 1.5000 | 每手固定额 |
| `DCE.m2705` | 3019 | 10 | 1.5000 | 1.5000 | 每手固定额 |
| `SHFE.rb2610` | 3100 | 10 | 0.3100 | 0.3100 | 按额，万分之 0.1 |
| `SHFE.rb2705` | 3189 | 10 | 0.3189 | 0.3189 | 按额，万分之 0.1 |
| `DCE.i2701` | 734.5 | 100 | 7.3450 | 7.3450 | 按额（率 `1e-4`） |
| `SHFE.cu2701` | 108330 | 5 | 27.0825 | 27.0825 | 按额（率 `5e-5`） |
| `SHFE.ag2702` | 16095 | 15 | 12.07125 | 12.07125 | 按额（率 `5e-5`） |

三条结论：

1. **两种收法真的并存。** 豆粕两个月份的昨结算价差 319 元而费额分毫不变 → 每手固定额；
   螺纹从 0.3100 变到 0.3189，与按比例的预测精确相符 → 按额。
   §7 开头那句「两项都要算并相加」不是防御性写法，是**被实测支持的**。
2. **本批六个合约的开仓档与平今档同额。** ⚠️ 这不能推广：平今费率可以远高于平昨，
   也可以为 0，只是这六个品种当天恰好相等。**平昨档一次也没测过**（需要昨仓）。
3. ⚠️ **按额那一档的基准价是昨结算价，不是成交价——这与真实 CTP 不同。**

第 3 条单独展开，因为它是本批实测里唯一一条**已知偏离真实柜台**的：

> 同一合约上一手买、一手卖，成交价 738.50 与 738.00 相差一个 tick，
> 两笔手续费**完全相同**，都是 7.3450 = 734.50 × 100 × `1e-4`（734.50 是昨结算价）。
>
> CTP 的 `单笔手续费 = 成交量 × 成交价 × 乘数 × ByMoney + ...` 用的是**成交价**。
> 快期模拟只维护「每手手续费」这一个日初预算好的数，与成交价无关。

⚠️ **这个偏差在同一天之内是一个常数**，因此对拍时极容易被读成「对上了」：
成交价与昨结算价通常只差千分之几，单笔差额是厘级的。
它要靠**跨越结算日**的长链对拍才会累积到可见，而那正是最少被跑的一类用例。

⚠️ 判据说明：「按昨结算价比例」与「每手固定额」在**单个合约**上给出同一个数，
怎么测都分不开——必须同品种、两个昨结算价不同的合约。
样本守卫放在跑完之后，用实测费额复核「按比例的预测差是否高于字段分辨率」，
差得不够就报判据不成立，而不是给一个看起来合理的结论。

### 手续费的取整（**待实测**；「到分」两个候选已被排除）

按金额算出来的手续费几乎必然是无限小数。柜台在哪一步取整、取到几位、
四舍五入还是截断？候选：四舍五入到分 / 截断到分 / 不取整。

判别实验：构造一笔手续费理论值恰好在半分附近的成交，看 `Commission` 的取值。
偏差单笔只有几厘，但**逐日累加进结存**，长周期回测会漂出可见的量。

**交易日 20260908 的夜盘（快期模拟·取值）：`SHFE.ag2702` 的每手手续费是 `12.07125`。**

16095（昨结算价）× 15（乘数）× `5e-5` = 12.07125，**五位小数原样保留**。
冻结值与实收值都是这个数。于是「四舍五入到分」与「截断到分」**都被排除**。

⚠️ **但这一条不算收敛，理由有两条：**

1. 剩下的候选「不取整」与「取整到 5 位以下的某个精度」在本样本上**分不开**——
   12.07125 本身恰好就是 5 位，再细的位数没有被考验过。
2. 这只是**一个柜台**的取值。取整口径是各柜台自定的，
   而本批实测里已经量到快期在手续费基准价上**偏离真实 CTP**（见上一节），
   所以「快期这样」不能直接读成「规则如此」。

⚠️ 顺带记一个工具上的坑：这个数最初被我的探针打成 `12.0712`——
因为打印格式是 `%.4f`。**显示取整正好会盖住柜台取整**：
柜台报 12.07125 而我看到 12.0712 时，「柜台取到 4 位」与「柜台没取整、是我截的」
长得一模一样。**一个观测工具的精度低于被观测量时，它测的是自己。**

## 8. 资金账户与逐日盯市

### 结存链条（**文档**）

```
今结存 Balance = 上日结存 PreBalance
               + 入金 Deposit − 出金 Withdraw
               + 平仓盈亏 CloseProfit
               + 持仓盈亏 PositionProfit
               − 手续费 Commission
```

盘中 `PositionProfit` 是浮动的，于是 `Balance` 盘中就是**动态权益**；
日终结算把浮盈兑现，`Balance` 成为静态结存，并作为明日的 `PreBalance`。

```
可用资金 Available = Balance − CurrMargin − FrozenMargin − FrozenCash − FrozenCommission
风险度            = CurrMargin / Balance
```

`FrozenMargin` / `FrozenCommission` 是**未成交报单**冻结的保证金与手续费，
`FrozenCash` 是期权权利金冻结（v1.0 不涉及）。

**交易日 20260908 的夜盘实测（快期模拟·取值）：三条恒等式在 float64 表示误差内成立。**

⚠️ 更正：此处**原本写的是「精确成立」**。那是在小数点后 4 位的打印精度下看到的。
夹具里存着 `commission: 126.95459999999999` 这类 float64 往返噪声，
全精度下最大残差约 `1e-10`。「表示误差内成立」比「精确成立」弱，但它是真的。
核对已落成 `TestAccountIdentitiesHoldOnEveryFixture`，跑遍**每一份**账户截面夹具，
判定容差 `1e-9`，另有一道**不随容差移动**的兜底阈值 `1e-6`。
两者都被要求比最小有意义金额 `1e-4` 小两个数量级以上，
而这条要求本身已落成断言（`TestToleranceOrderingIsAsserted`）——
⚠️ 「残差顶到容差时该查账，不该调容差」不再是写给人看的忠告，
谁把容差调到接近真实金额，**干净仓库下就会红**。

以持有 4 手种子、当日已有平仓的一个截面为例：

```
static_balance 1000000.0000   close_profit -740.0000   commission 217.1312
position_profit 0.0000        margin 9186.8000

balance    = 1000000 - 740 + 0 - 217.1312 = 999042.8688   实测 999042.8688
available  = 999042.8688 - 9186.8000      = 989856.0688   实测 989856.0688
risk_ratio = 9186.8 / 999042.8688         = 0.00919...    实测 0.0092（四位）
```

还有一条是靠**旧夹具**才测出来的：

```
2026-09-07  pre_balance 0        deposit 1000000  static_balance 1000000
2026-09-08  pre_balance 1000000  deposit 0        static_balance 1000000
```

→ **`static_balance = pre_balance + deposit − withdraw`**，出入金已被静态权益吸收。

⚠️ 我第一版核对写成 `balance = static_balance + deposit − withdraw + ...`，
于是 09-07 那两份夹具整整差了 100 万——**入金被算了两遍**。
上面那条 CTP 形式的公式用 `PreBalance`，是对的；错的是我把两种写法的项混在了一起。

⚠️ **这条关系只在入金非零的那天测得出，而整批夹具里只有 09-07 的两份满足。
当初若嫌旧把它们删了，这一条今天就无从验证。**

⚠️ 三条各自的判别力不一样，必须分开说：

- `balance` 一条里，`position_profit` 与 `float_profit` **在今仓上恒等**，
  所以「结存用的是哪一个」**没有测出来**。要分开同样得等昨仓。
- ⚠️ **`− withdraw` 这一项一次也没参与过运算**：所有夹具的出金都是 0。
  一个恒为 0 的减项不会暴露自己被漏掉。模拟账户不能出金，此项只能等真实柜台。

**CTP 的两个账户级参数，一个已被排除到唯一取值，另一个完全没有判别力：**

`CThostFtdcBrokerTradingParamsField` 上除了 `MarginPriceType`，还有两个直接决定
权益怎么算的字段。它们此前不在本文档里——是核实评审那条重新框定时顺带撞见的：

| 字段 | 取值 | 本批证据能说什么 |
|---|---|---|
| `Algorithm`（盈亏算法） | `'1'` 浮盈浮亏都计算 / `'2'` 浮盈不计浮亏计 / `'3'` 浮盈计浮亏不计 / `'4'` 都不计 | ✅ **排除到 `'1'`**：夹具里浮盈 6 份、浮亏 6 份，结存恒等式**两边都成立** —— `'2'` 会漏掉浮盈、`'3'` 会漏掉浮亏、`'4'` 两头都漏 |
| `AvailIncludeCloseProfit` | `'0'` 包含平仓盈利 / `'2'` 不包含 | ⚠️ **完全没有判别力**：所有夹具的 `close_profit` 都是**负数**，而这个参数只在平仓盈利**为正**时才分得开 |

⚠️ 第二行正是「一个恒为某号的量不会暴露参数被漏掉」的实例，
而它躲过了我此前所有的人工核对——**因为我从没问过「这个数为正时会怎样」**。
判别力报告已落成断言：核对测试会把「浮盈几份 / 浮亏几份 / 平仓盈利为正几份 /
有冻结几份 / 有入金几份 / 有出金几份」逐项打出来，缺哪一类就明说哪一类空转。
- `available` 一条里，四个冻结项当时**全部为 0**。
  一个恒为 0 的减项不会暴露自己被漏掉，所以那次只验证了 `balance − margin` 这一半。
  **这个缺口当晚补上了**，见下。
- `risk_ratio` 只有四位小数，`margin / balance` 与 `margin / (balance − 某个小量)`
  在这个精度上分不开。要更强的证据得让风险度大一些。

### 挂单冻结（**实测（快期模拟·取值）**）

在 `SHFE.rb2610` 的跌停价上挂一手买单（挂得住、不成交），前后各取一次账户截面：

| | `balance` | `available` | `margin` | `frozen_margin` | `frozen_commission` |
|---|---|---|---|---|---|
| 挂单前 | 998641.9010 | 989455.1010 | 9186.80 | 0 | 0 |
| 挂单中 | 998641.9010 | 987284.7910 | 9186.80 | **2170.0000** | **0.3100** |
| 撤单后 | — | — | 9186.80 | 0 | 0 |

四条结论：

1. **冻结项确实从 `Available` 里扣**：`available` 精确减少 2170.3100，
   等于两个冻结项之和。§8 那条公式的后半段成立。
2. **`balance` 分毫不动**：冻结只占用可用，不进结存。
3. **挂单不进 `margin`**：`margin` 全程 9186.80。冻结与持仓保证金是两个口子。
4. **撤单后完整释放**：`available − balance` 回到 −9186.8000，差 `0.000000`。

另外两个数各自说明一件事：

- `frozen_margin = 2170.0000` **正是该合约每手持仓保证金**（昨结算价 3100 × 10 × 7%）。
  按委托价（跌停 2945）算应是 2061.50。→ **冻结保证金按昨结算价，不按委托价。**
- `frozen_commission = 0.3100` 正是该合约的开仓手续费。→ 手续费也被冻结。

⚠️ 判据四曾经差点被读错。首跑时撤单后 `available` 比挂单前少 20，
看起来像「有 20 块没还回来」——实际是账上**别的持仓**（过夜种子）在这几秒里浮亏了 20，
同期 `balance` 也正好少 20。判据改用 `available − balance`，把浮盈亏消掉之后才干净。
⚠️ **一个绝对量的判据，会把「环境在动」读成「被测对象出错」。**

⚠️ `FrozenCash`（期权权利金冻结）与 `frozen_premium` 全程为 0，
本批**没有测到**——它们属于 §12 明确不建模的期权范围。

⚠️ **报单冻结必须建模。** 挂单占用可用资金但不占用 `CurrMargin`，
不建模会让回测在「挂了一堆单」的状态下以为自己还有钱，从而开出真实账户开不出的仓。

### 日终结算的执行顺序（**推得**）

顺序不是随意的，每一步都依赖前一步的结果：

```
1. 交易所公布今结算价
2. 按今结算价算持仓盈亏（昨仓以昨结算价为基线，今仓以开仓价为基线）
3. 汇总当日平仓盈亏与手续费
4. 结出今结存 Balance
5. 按今结算价重算保证金占用（含大边、交割月递增）
6. 判风险度 → 追保通知 / 强平标记
7. 今仓 → 昨仓，昨结算价 ← 今结算价，逐笔明细的结算基线一并推进
8. 生成结算单
```

第 5 步必须在第 4 步之后：保证金用今结算价重算，而权益也是今结算价口径，
两者错位会让风险度在结算当天跳一下又跳回来。

第 7 步是**唯一**把「今」变成「昨」的地方。它一旦漏掉或重复执行，后续每一天的
平今/平昨判定、手续费、保证金基线全部错位，而且**不会报错**——
账还是平的，只是平在错的地方。

## 9. 报单校验

按拒绝的优先级（**文档**；前三项 20260909 有了实测支撑，见下面「拒绝优先级」一节）：

| 校验 | 依据 |
|---|---|
| 合约是否可交易 | `IsTrading` `InstLifePhase` |
| 是否在交易时段内 | 交易日历 + 品种时段表（含夜盘） |
| 价格是否为最小变动价位的整数倍 | `PriceTick` |
| 价格是否在涨跌停之内 | 昨结算价 × (1 ± 涨跌幅) |
| 手数是否在上下限内 | `MinLimitOrderVolume` `MaxLimitOrderVolume`（市价单另有一组） |
| 平仓量是否超过可平量 | 今昨仓分别校验 |
| 可用资金是否够 | 保证金 + 手续费 |
| 限仓 | 交易所限仓规则 |

⚠️ **平仓量校验必须按今昨分别做。** 昨仓 3 手、今仓 5 手，报「平昨 4 手」应当被拒，
即使总持仓有 8 手。合并校验会放过它，然后在结算时算出一个不存在的持仓。

（参照仓库在这里栽过：超量平仓被当成反手，10 张平 4 张多头得到 6 张多头，
「想平仓，仓位反而变大」，全程不报错。中国期货不允许反手，所以这里只有一个正确答案：
**拒绝**。）

### 报单被拒时柜台的原话（**实测（快期模拟·语义）**）

2026-09-07 在**快期模拟**上构造五类反例，逐条记下柜台返回的 `last_msg`。
⚠️ 来源是快期模拟不是 CTP 柜台，**拒因文案在真实柜台上可能不同**；
这里能立住的是「哪些输入会被拒」与「`CLOSE` 被解释为平昨」这两条语义，
不是文案本身。CTP 的数值错误码要等 SimNow 那一轮。
原始夹具：`testdata/probes/exp6-reject-code-20260907.json`，
复跑：`cd cmd/oracle && ./oracle probe -exp reject-code -symbols SHFE.rb2701`。

| 构造的反例 | 柜台原话 |
|---|---|
| 限价 > 涨停价 | `已撤单报单被拒绝价格超出涨停板` |
| 限价 < 跌停价 | `已撤单报单被拒绝价格跌破跌停板` |
| 空仓上报「平仓」 | **`平昨手数超过昨仓持仓量`** |
| 空仓上报「平今」 | `平今手数超过今仓持仓量` |
| 限价不是最小变动价位整数倍 | `下单价格不是价格单位的整倍数` |

⚠️ **第三行是意外收获，而且是本轮最有价值的一条。**
在 SHFE 合约上报**普通平仓**，柜台答的是「平**昨**手数超过**昨仓**持仓量」——
说明 `Offset=CLOSE` 在 `UseHistory` 的交易所上被直接解释为**平昨**，
不是「由柜台自行决定平今还是平昨」。这条**直接支持** §4 里
「`UseHistory` 合约必须显式声明平今或平昨」的建模，并且把默认语义钉死了：
不声明 = 平昨 —— ⚠️ **但只在快期模拟上成立**，
本库在 SimNow 复核前对裸 `CLOSE` 报错而非按此处理，见 §4。

⚠️ 有三类校验**没有**构造进来，是有意排除而非遗漏。⚠️ **其中一条的理由已经过期，**
**而它在这里原样躺了两天**：

    手数上下限   原写「免费行情不下发 max/min_limit_order_volume」。
                 ⚠️ 那是**行情流**不下发；`refdata-sync -specs` 产出的规格文件里
                 两个字段都有（`testdata/refdata/specs-20260908.json`，
                 例如 SHFE.ag2702 的 max=500、min=1）。
                 真正拦住它的是**另一件事**：超上限的开仓单会先被探针的安全阀
                 （`PROBE_MAX_VOLUME=1`）拦下，根本到不了柜台；而调松安全阀
                 去测一条规则，是拿真账户换一条观测。⚠️ 平仓单不受该上限约束，
                 所以这一项**只能**与「超可平量」一起测，测不出单独的它。
    限仓         需要交易所限仓额度，规格文件里没有。
    可用资金不足 要把账户打到接近爆仓，会污染后续实验的起点。

**列出来是因为一份看起来完整的清单最容易掩盖缺口** —— ⚠️ 而这次的教训更细一层：
**一条写下来的排除理由本身也会过期，且它过期时同样不会有任何动静。**

### 拒绝优先级（**实测（快期模拟·语义）**，与上表一致）

2026-09-09 凌晨在**快期模拟**上构造「同时违反两项」的单子，看柜台回哪一个
`last_msg`。SHFE.ag2702（tick=1）与 DCE.i2701（tick=0.5）各一遍。

| 越涨停 + 超可平量 | 越涨停 |

于是三项的先后是：**最小变动价位 > 涨跌停 > 可平量**，与上表一致。

⚠️ 实验里那层「违规真的构造出来了吗」的核对**没能拦住**，因为它用的是
**本库的**判据，而分歧恰恰在判据本身。

> **一个用自己的定义去核对自己的守卫，对「定义分歧」没有判别力。**

⚠️ 三处边界，一处都不能省：

    两个合约、两家交易所、一个口子   换 CTP 要重测（simnow_pending#11）

### 柜台的第二条回话通道：`notify`（**实测（快期模拟·实现）**）

    code=412  下单,已被服务器拒绝, 原因:<拒因>     ← 拒因文案与 last_msg 相同
    code=401  连接/登录类的 INFO

⚠️ 后果要写下来：**本仓库此前所有的拒因实验都只读委托记录**。
一条只走 notify 的拒绝，在那些实验里长得像「柜台没反应」——
而那与「单子还挂着」长得一模一样。

⚠️ 这些是**天勤自己的**码，不是 CTP 的 `ErrorID`，**填不了 `ctperr`**
（simnow_pending#5）。⚠️ 原先那条待办写的是「快期模拟给的是中文文案」——
那句话不准：不是「没有码」，是「码不是那一套」。
**一个理由说错了的待办，会让下一个人去找一个本来就不存在的东西。**

拿这条通道当归因依据，「合约不可交易」这一项的位次也就问得出来：
不存在的合约 + 偏离整数倍的价 → 回 311 而不是 412，
即**合约排在价格类校验之前**，与上表一致。

⚠️ 夹具只收 `type`/`level`/`code`，**刻意不收 content**：白名单靠逐个字段
点名来保护，而 content 是服务器写的自由文本 —— 一个自由文本字段
从原理上就不在白名单的保护范围内，而仓库是公开的、泄漏不可逆。
文案由人工看过之后写进上面的表。**收不收 content 是一个要人来定的取舍。**

### 价格零头 < 半个 tick 才算「不是整数倍」（**实测（快期模拟·实现）**，⚠️ 已知偏离）

同一时刻、同一合约、同一越界幅度，只扫价格零头：

| 零头（单位：一个 tick） | 柜台 |
|---|---|
| 0 | 收下（价内）／报涨跌停（越界） |
| 1/10 | **报「下单价格不是价格单位的整倍数」** |
| 1/3 | **同上** |
| 1/2 | 收下（价内）／报涨跌停（越界） |
| 7/10 | 同上 |
| 9/10 | 同上 |

SHFE.ag2702（tick=1）与 DCE.i2701（tick=0.5）两遍，边界都落在**半个 tick**上
——所以它**随 tick 缩放**，不是某个绝对数。被收下的委托记录里还留着那个带零头的
价，例如 `limit_price=13009.9`。

⚠️ **这几乎肯定偏离真实 CTP**：交易所侧任何非整数倍的报价都要被拒。
本库按交易所口径**一律拒绝**，把这条记为已知偏离（simnow_pending#11）。

⚠️ 它的第二个用处是**划出一个陷阱**：拿零头 ≥ 半个 tick 的价格去构造
「不是整数倍」这一违规，构造出来的单子**柜台根本不认为违规**——
上一节那次翻案就栽在这里。

### 涨跌停（**文档**）

```
涨停价 = 昨结算价 × (1 + 涨跌幅比例)，按最小变动价位取整
跌停价 = 昨结算价 × (1 − 涨跌幅比例)，按最小变动价位取整
```

基线是**昨结算价**，不是昨收盘价。连续涨跌停会触发扩板与保证金上调，
这是规则数据而非公式，v1.0 不建模（见 §12）。

## 10. 风控：追保与强平

⚠️ **这一节与加密货币有本质区别，是本项目最重要的一条边界。**

OKX 的强平是**交易所的确定性算法**：保证金率跌破阈值，撮合引擎立刻按既定链路执行，
输入相同则输出相同，可以被 100% 复现。

中国期货**不是**。链路是：

```
风险度 ≥ 100%  →  期货公司发追保通知  →  客户在规定时间内（通常次日开盘前）补足或自行减仓
                                      →  未补足 → 期货公司执行强平
```

其中「规定时间」「强平的下单方式」「先平哪个合约」「一次平多少」**全部由期货公司的
风控制度决定，各家不同，且含人工环节**。CTP 的平仓标志里同时有「交易所强平」
「强减」与「本地强平」三种取值，正说明它不是单一算法。

**因此本库的立场是：**

- **建模「判据」**：风险度、可用资金是否为负、是否触发追保线——这些是确定的、可复现的
- **不建模「执行」**：强平的时点、顺序、数量不做假设。本库给出**信号**与**风险敞口**，
  由使用者按自己的风控制度决定怎么处理
- 提供一个**可选的**默认强平策略（按风险度降序平仓直到风险度回到阈值以下），
  明确标注为**约定而非还原**，且默认不启用

声称「100% 模拟强平」在中国期货语境下是不诚实的。本项目不会这么说。

## 11. 交割

| 类型 | 品种 | 处理 |
|---|---|---|
| 实物交割 | 商品期货 | ⚠️ **自然人客户不得进入交割月**，须在规定时点前平仓，否则被强制平仓 |
| 现金交割 | 股指期货 | 按交割结算价现金了结 |
| 实物交割 | 国债期货 | 券款对付，v1.0 不建模交割流程 |

交割结算价各所规则不同（股指为最后交易日标的指数最后两小时算术平均价，
商品多为交割月内结算价的加权平均）。**本库不计算交割结算价，由外部提供**，
理由同结算价：它是交易所的结算结果，不是行情。

v1.0 建模到「交割月保证金递增 + 自然人持仓限制的告警」，不建模实物交割的仓单流转。

## 12. 明确不建模

| 项 | 理由 |
|---|---|
| 结算价的计算 | 是交易所的结算结果，各所规则不同且含无成交时的特殊处理。由外部提供 |
| 盘口深度、排队、部分成交 | 没有逐笔委托数据就无从建模，硬造只会给出看似精确实则杜撰的结果 |
| 期权 | 保证金模型完全不同（权利金、Delta、组合保证金）。v1.0 外 |
| 组合保证金 / 套利组合 | 需要交易所的组合定义与审批数据，回测拿不到。v1.0 外 |
| 连续涨跌停的扩板与临时保证金上调 | 是交易所的临时公告，非公式。可由使用者通过规则数据注入 |
| 银期转账、出入金的到账时点 | 与交易核算无关 |
| 强平的执行 | 见 §10 |

### ⚠️ 第 11 条的构造成本随时间涨，所以它有一个执行顺序

`close_profit` 是**当日累计**字段，不是单笔。2026-09-08 这个交易日跑完全部实验之后，
账户的累计值是 **−1190**——要把它翻正，得再净赚 1190 元。
在 `cu` 上约合 24 个 tick，**那是一笔真实的方向性下注，而且同样可能反向走。**

⚠️ **不值得为一次测量去下这个注。** 理由不只是「贵」：
**成本无上界，而且结果会被同一个随机性毁掉**——赌赢了，拿到的是一个
「刻意做多 `cu`」条件下的观测；赌输了，既没测到、又把累计值推得更负、下次更贵。
⚠️ **一个需要押注才能构造的样本，它的成本和它的效度会一起随行情走。**

便宜得多的那条路建立在下面这句话上：

> **`close_profit` 在日终结算时归零**（**推得**，非实测）——
> 若成立，新交易日里一笔赚 1 个 tick 的往返就够。

⚠️ **这句话此前是裸的，是这份文档里唯一一条不带证据等级的规则性陈述**，
而第 11 条的便宜路径、以及由它推出的整个执行顺序，全部压在它上面。
它的实际等级最多是**推得**：从「当日累计」推出「日终归零」。
⚠️ 本项目已经栽过一次同型推理——「快期的率都是 7%」也是从一批观测推出来的。

**手上一份直接证据都没有**：2026-09-07 的 `close_profit` 确实是 0，
但那天**根本没有平仓成交**，0 是初始值，不是「跨结算归零」的观测。
真正的证据要看一次**带着非零值跨过结算**的转变，而那要到 20260909 才有。

✅ **好消息是它零成本可验**，就在第 0 步：新交易日读一次账户即可。
`close_profit == 0` 就地把这句话从**推得**升成**实测**；
若它仍是 −1190，**第 11 条的便宜路径当场作废**——那时该做的是跳过它去跑昨仓批，
而不是在窗口里追一个已经不成立的前提。

于是它有了一个执行顺序，而这个顺序是**单向**的：

> 第 11 条必须排在**新交易日的最前面**，早于任何别的实验。
> 每一条实验都会因手续费与买卖价差**净亏**，累计值只会越跑越负；
> 一旦跑过几条，构造成本就从「1 个 tick」涨到「几十个 tick」。

⚠️ 这一条和昨仓那批（#1/#2/#4/#7/#8/#10）落在**同一个窗口**——
过夜种子要等 20260908 结算之后才变昨仓，即交易日 20260909 起。
**两者共用窗口而顺序不可交换**：先第 11 条，再昨仓批。

⚠️ 更一般地：**判别样本的构造成本可能随时间单调上升**，
那时「先做哪一条」就不再是偏好问题。本文档此前默认实验之间彼此独立，
这是第一条不独立的。

⚠️ **这一夜量了很多，而这张表上一条也没划掉。** 这不是失败，是两件事被分开了：

- 量到的是**快期模拟这个口子怎么实现**（四条，见 [state.md](./state.md) 的 `kq_facts`）；
- 这张表问的是**规则是什么**。

三条新增项（8/9/10）全部是**由实测本身暴露**的：不去量，就不会知道
「开仓档等于平今档」只是当天六个品种恰好相等、
「`available = balance − margin` 对上了」只是因为四个减项当时都是 0。
⚠️ **实测的第一个产出往往不是答案，是一批更准的问题。**

## 14. 建模时的高风险点

按「出错时会不会有动静」排序，全部是**不会有动静**的那类：

1. **乘数漏乘** —— 金额量级看起来仍然合理
2. **今仓昨仓不滚动** —— 账是平的，只是平今费率一直按平昨收
3. **只存均价、不存逐笔明细** —— 逐笔对冲口径永远算不回来，且不报错
4. **单向大边按合约合并** —— 单合约样本上与正确答案同值
5. **盘中保证金用错价** —— 数字始终合理，只是追保线错位
6. **交易日按自然日推** —— 只在长假前后错，而那正是保证金上调的时候
7. **报单冻结不建模** —— 回测比真实账户「有钱」，开得出实际开不出的仓

这七条会各自对应一条守卫测试，并进入 [silent-risks.md](./silent-risks.md)。
